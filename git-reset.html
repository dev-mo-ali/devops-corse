01 / The foundation

The three trees of Git

Think of Git as managing three different views of your project. The Index is technically a staging manifest, but imagining three “trees” makes the reset sequence intuitive.

COMMITTED SNAPSHOT

HEAD

Usually a symbolic pointer to your current branch, which points to a commit. The HEAD commit represents the most recently recorded snapshot.

git ls-tree -r HEAD
PROPOSED SNAPSHOT

Index (Staging Area)

The file versions selected for the next commit. This snapshot can differ from both HEAD and the files you see in your editor.

git ls-files -s
EDITABLE FILES

Working Directory

The actual project files you edit in VS Code—such as your Laravel controllers, routes, and configuration.

git diff
Normal workflow: Edit a file in the Working Directory → git add copies its current content to the Index → git commit saves an Index snapshot and advances the branch.

03 / Reset commands

Soft, mixed, hard, and path-specific resets

MOVE BRANCH ONLY

Soft reset

git reset --soft HEAD~1

Moves the current branch to the target commit; leaves both the Index and Working Directory untouched. Useful when rebuilding a commit without unstaging its changes.

DEFAULT MODE

Mixed reset

git reset --mixed HEAD~1

Moves the branch and resets the Index to the target snapshot. Does not change the Working Directory. Your removed commit's changes become unstaged.

DESTRUCTIVE RISK

Hard reset

git reset --hard HEAD~1

Moves the branch, resets the Index, and replaces tracked working files to match the target. Check git status and protect local work before running it.

FILE-LEVEL RESET

Reset a specific file

git reset HEAD -- routes/web.php

Does not move HEAD. It resets that file's Index entry from HEAD while leaving its working copy untouched. Modern equivalent: git restore --staged routes/web.php.

04 / Recovery playbook

How to undo each type of reset

There is no single “cancel reset” command. A completed reset can often be reversed by finding the previous commit with git reflog and moving the branch back—but preserving your current working changes matters.

Before any reset: Record the current commit with git rev-parse HEAD. Immediately after many commit-level resets, ORIG_HEAD records the previous HEAD; verify it with git show --no-patch --oneline ORIG_HEAD. ORIG_HEAD can be overwritten by subsequent operations, so reflog is your fallback.
UNDO SOFT

1. Undo git reset --soft HEAD~1

Soft reset changed only the branch. If nothing else changed and you want to restore the previous commit while leaving Index and working files exactly as they are, use another soft reset targeting the original commit.

git reflog -5 git show --no-patch --oneline ORIG_HEAD git reset --soft ORIG_HEAD git status

If ORIG_HEAD is no longer the correct commit, substitute the verified SHA from git reflog. Your staged and working changes remain as they were.

UNDO MIXED

2. Undo git reset --mixed HEAD~1

A mixed reset moved the branch and reset the Index, but left files alone. When the working files still match the old commit and you have made no additional edits, move the branch back and restage the original snapshot:

git reflog -5 git show --no-patch --oneline ORIG_HEAD git reset --soft ORIG_HEAD git restore --source=ORIG_HEAD --staged :/ git status

This restores the old HEAD and stages its tree, without overwriting your working files. It does not reconstruct any custom staging state you had before the mixed reset; Git does not keep a general-purpose history of the Index.

UNDO HARD — CAUTION

3. Undo git reset --hard HEAD~1

If the lost version was committed, Git often still knows that commit through reflog. First inspect and verify the original commit. Then use a hard reset only if there is no new work to preserve:

git status git reflog -10 git show --stat <old-commit-sha> git reset --hard <old-commit-sha>
This can restore the old committed snapshot, but it cannot reliably recover unsaved/uncommitted edits overwritten by the first hard reset. If you have created new work since then, save it to another branch or stash it first; do not blindly run another --hard.

A safer inspection option: git switch -c recovered-work <old-commit-sha> when your working tree is clean. That creates a branch at the recovered commit without moving your original branch.

UNDO FILE RESET

4. Undo an accidental git reset HEAD -- file.txt

If the file's working copy still contains the change that was unstaged, simply stage it again:

git add -- file.txt git status

This stages the file's current full content, which may differ from the originally staged selection if you made further edits.

RESET VS MERGE ABORT

5. Reset is not an in-progress merge

git merge --abort cancels an in-progress merge. It does not undo a completed git reset. For a reset that already finished, inspect reflog and choose a recovery approach appropriate to the state you want to preserve.

05 / Hands-on lab

Practice in a disposable repository

Run these exercises in a brand-new directory, not in a production repository. Configure your Git author identity first if needed.

Create three snapshots

mkdir git-reset-lab && cd git-reset-lab && git init echo A > file.txt git add file.txt && git commit -m "A" echo B > file.txt git add file.txt && git commit -m "B" echo C > file.txt git add file.txt && git commit -m "C"

All three trees now represent version C.

Try soft reset and undo it

git reset --soft HEAD~1 git log -1 --oneline git diff --cached git reset --soft ORIG_HEAD git status

You'll move from C to B, see staged differences, then restore the branch to C without touching the Index or files.

Try mixed reset and undo it

git reset --mixed HEAD~1 git status --short git diff git reset --soft ORIG_HEAD git restore --source=ORIG_HEAD --staged :/ git status

The working file remains C while the Index becomes B; then return HEAD and the Index to C.

Inspect snapshots and reflog

git log --oneline git ls-tree -r HEAD git ls-files -s git status git reflog

Inspect the three-tree model and the reference movement history directly.

06 / Real-world decisions

Which command should I choose?

Forgot a file in the last local commit

git reset --soft HEAD~1 git add forgotten.php git commit -m "Complete feature"

Accidentally staged a file

git restore --staged routes/web.php

Squash two local commits

git reset --soft HEAD~2 git commit -m "Complete feature"

Use with care if the commits have already been shared.

Undo a published shared commit

git revert <commit-sha>

Creates a new inverse commit and preserves the shared history.

Additional safety note: git reset --hard does not generally remove all untracked files, but it can remove untracked files or directories obstructing paths being written. Reflog helps recover commits, not arbitrary uncommitted changes.
