6.2 · Authentication lesson

Sign in to your account

Browser, GitHub Desktop, API, and command-line access can use different credentials.

  1. In a browser, sign in with the method supported by your account, such as a password or passkey.
  2. GitHub Desktop can complete sign-in through your browser.
  3. Organization access may also require single sign-on.

Source: GitHub Docs · About authentication ↗

6.2 · Authentication lesson

Add another layer of protection

Two-factor authentication helps protect sign-in even if a password is compromised.

  1. Set up an available second factor or passkey in account settings.
  2. Store recovery codes somewhere you can reach if a device is lost.
  3. Keep recovery methods current before changing devices or authentication methods.

A passkey can satisfy both password and two-factor requirements for supported personal accounts.

Source: GitHub Docs · About 2FA ↗

6.2 · Authentication lesson

Authenticate Git over HTTPS

Account passwords are not accepted for Git operations over HTTPS.

  1. Use GitHub CLI or a credential helper when that fits your workflow.
  2. If a personal access token is needed, prefer a fine-grained token where supported.
  3. Limit repository access and permissions, set an appropriate expiration, and protect the token like a password.

Source: GitHub Docs · Personal access tokens ↗

6.2 · Authentication lesson

Connect with an SSH key

SSH uses a key pair to authenticate Git access without entering a token for every operation.

  1. Check for an existing key or generate a new key pair on your device.
  2. Add the public key to your GitHub account and protect the private key.
  3. Test the SSH connection and use an SSH remote URL.

Source: GitHub Docs · Connecting with SSH ↗

6.4 · Releases lesson

Understand the three pieces

A tag identifies the source version; a release adds a useful distribution page.

PieceWhat it provides
Git tagA name for a point in repository history, such as v1.4.0.
ReleaseA title, description, publication state, and files associated with that tag.
AssetAn attached download, such as a compiled application or archive.

A tag can exist without a release. Tag creation and release publication can happen on different dates.

Sources: About releases ↗

6.4 · Releases lesson

Choose what users download

GitHub supplies source archives; you attach built packages separately.

  1. The release includes ZIP and tar.gz source downloads for the tag.
  2. Attach the files users need to install or run your version.
  3. Use clear filenames so readers can choose the correct platform or package.
LimitCurrent documented value
Assets per releaseUp to 1,000
Individual file sizeUnder 2 GiB
Total release size and bandwidthNo stated limit

Repository administrators control whether generated archives include Git LFS objects.

6.4 · Releases lesson

Set the release state deliberately

Saving work, marking a preview, and choosing the latest version serve different purposes.

ChoiceUse it for
Save draftKeep preparing the release before publication.
This is a pre-releaseTell users the version may be unstable and is not ready for production.
Set as latest releaseChoose the release used by the latest-release link.

6.4 · Releases lesson

Finish the assets before publishing

When release immutability is enabled, publication locks the release’s tag and assets.

  1. Prepare the release as a draft and attach every intended file.
  2. After publication, assets cannot be added, replaced, or removed.
  3. The tag cannot move or be deleted while the release exists.
  4. Titles, release notes, and pre-release/latest labels remain editable.

Deleting an immutable release does not make its tag name reusable. Publish a new version when the software or package must change.

An immutable release also receives an attestation that records its tag, commit, and assets.

Sources: Immutable releases ↗

6.4 · Releases lesson

Make the target explicit

Run these examples in your repository with GitHub CLI installed and authenticated.

EXAMPLE · EXISTING REMOTE TAG AND LOCAL BUILD FILE
gh release create v1.4.0 dist/my-app.zip --verify-tag --draft --title "1.4.0" --generate-notes
  1. --verify-tag stops creation if the tag is missing from the remote repository.
  2. --draft leaves the release unpublished for review.
  3. The file argument uploads an existing local build; it does not compile your application.

Without --verify-tag, a missing tag is created from the default branch unless --target specifies another branch or commit.

Sources: CLI · release create ↗

6.4 · Releases lesson

Review, then publish the draft

Check the draft before changing its publication state.

EXAMPLE · REVIEW AND PUBLISH
gh release view v1.4.0 --web
gh release edit v1.4.0 --draft=false
EXAMPLE · INSPECT THE PUBLISHED RELEASE
gh release view v1.4.0
gh release view v1.4.0 --json tagName,isDraft,isPrerelease,url,assets

The first command opens the release page. The edit command publishes the existing draft. Inspect the resulting version and its attached files.

6.4 · Releases lesson

Maintain the published information

Use the release’s edit control to correct details, then save the update.

EXAMPLE · CHANGE TITLE OR NOTES
gh release edit v1.4.0 --title "1.4.0 — Export improvements"
gh release edit v1.4.0 --notes-file release-notes.md

To remove a release, use its delete control and confirm the action, or run:

DESTRUCTIVE EXAMPLE · CONFIRM THE VERSION FIRST
gh release delete v1.4.0

The CLI keeps the tag unless you explicitly request --cleanup-tag. Avoid --yes when you want the confirmation prompt. Immutable releases still impose tag restrictions.

Compare the right branches

The base receives the change; the head contains your proposed commits.

  1. Open Pull requests and choose New pull request.
  2. Confirm the base repository and branch, then the compare branch.
  3. Review the diff, write a clear title and description, and create the pull request.

Source: GitHub Docs · Creating a pull request ↗

6.5 · Lesson

Signal whether the work is ready

A draft pull request invites early discussion before a final review.

  1. Open a draft when you want feedback on work in progress.
  2. Push additional commits to the head branch as the work evolves.
  3. Mark the pull request ready for review when the change is prepared for a decision.

Source: GitHub Docs · Creating a pull request ↗

6.5 · Lesson

Inspect and discuss the diff

Reviewers can leave comments, suggest edits, approve, or request changes.

  1. Read the description and inspect the Files changed tab.
  2. Comment on specific lines and submit a review with an overall decision.
  3. Check the conversation and automated checks before deciding to merge.

Source: GitHub Docs · Reviewing pull requests quickstart ↗

6.5 · Lesson

Improve the pull request

Follow-up commits and clear replies keep the review moving.

  1. Read each comment and clarify anything ambiguous.
  2. Make the needed edits, test them, and push commits to the same head branch.
  3. Reply to review threads and request another review when appropriate.

Source: GitHub Docs · Resolving reviews ↗

6.5 · Lesson

Keep the branch mergeable

Changes in the base branch can make a pull request out of date or cause conflicts.

  1. Update the pull request branch when current base changes need to be incorporated.
  2. Resolve simple competing line changes in GitHub when the conflict editor is available.
  3. For other conflicts, resolve them locally and push the result.

Source: GitHub Docs · Resolving a merge conflict ↗

6.5 · Lesson

Finish with the right outcome

Merge when requirements pass and the change is accepted; close a proposal that should not land.

  1. Confirm required reviews, checks, and branch rules are satisfied.
  2. Choose an available merge commit, squash, or rebase method according to the repository workflow.
  3. Close without merging when the proposed change is no longer needed.

Source: GitHub Docs · Merging a pull request ↗

6.7 · Actions lesson

Understand the moving parts

A workflow is a YAML file that tells GitHub when and how to run automated work.

EventStarts a workflow run.
→
JobRuns on a selected runner.
→
StepRuns a command or reusable action.

Workflow files live in .github/workflows. A repository can contain multiple workflows.

Source: GitHub Docs · Understanding Actions ↗

6.7 · Actions lesson

Run a small workflow

Commit a YAML file under .github/workflows to make it discoverable.

.github/workflows/hello.yml
name: Hello Actions
on: [push]
permissions:
  contents: read
jobs:
  hello:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Hello from Actions"

Push the file, then open the repository’s Actions tab to inspect the run. This example only prints a message.

Source: GitHub Docs · Actions quickstart ↗

6.7 · Actions lesson

Choose where jobs run

Each job runs on a runner; its steps execute in order on that runner.

GitHub-hosted

Use a fresh hosted virtual machine, such as ubuntu-latest, windows-latest, or macos-latest.

Self-hosted

Operate your own runner when you need a different environment or specific hardware.

Separate jobs can run in parallel unless you define a dependency between them.

Source: GitHub Docs · Understanding Actions ↗

6.7 · Actions lesson

Automate a delivery path

Use workflows to validate proposed changes and publish approved work.

  1. Run build or test jobs when a pull request is opened or updated.
  2. Require useful checks before merging into an important branch.
  3. Deploy from a suitable event, such as a merge or release, using the required environment controls.

Match triggers and permissions to what each job must do.

Source: GitHub Docs · Understanding Actions ↗

6.7 · Actions lesson

Keep the right outputs

Artifacts preserve files produced by a workflow run; caches speed up repeated dependency downloads.

Artifact

Save test reports, build output, or files another job needs.

Cache

Reuse dependencies or other reproducible data across runs.

Do not put sensitive data in a cache.

Source: GitHub Docs · Workflow artifacts ↗

6.7 · Actions lesson

Limit workflow access

Workflows can read code, use credentials, and run third-party actions, so give each job only the access it needs.

  1. Grant the built-in GITHUB_TOKEN the minimum required permissions.
  2. Store sensitive values as secrets and avoid printing them in logs.
  3. Review third-party actions and treat untrusted pull request code carefully.

Source: GitHub Docs · Secure use ↗

6.7 · Actions lesson

Follow a run to the failing step

The Actions tab shows runs, jobs, steps, and logs that explain what happened.

  1. Open the workflow and select a run.
  2. Read the job status and expand the failed step’s log.
  3. Fix the workflow or project, then run it again and compare the result.

Build artifacts and logs can also be downloaded when you need to inspect them locally.

TERMINAL · IN YOUR CLONED FORK OR SHARED REPOSITORY
git status

# Edit and commit your changes
git add README.md

6.12 · Contributing to a Project

Make the review clear

  1. On GitHub, choose the correct target repository and base branch, then select your source branch.
  2. Describe the problem, the proposed change, and the checks you ran.
  3. Read review comments and automated check results; make and push follow-up commits to the same branch.
  4. Once the project’s requirements are met, an authorized person can merge or close the request.

Confirm the base and source before opening the request. A pull request can target a branch in the same repository or an upstream repository.

6.13 · Maintaining a Project

Evaluate a pull request

  1. Confirm the change’s purpose, target branch, and scope.
  2. Inspect the diff and commit history; consider security, compatibility, and project conventions.
  3. Review test results and run additional checks appropriate to the change.
  4. Discuss revisions, then merge using the project’s chosen method when requirements are satisfied.

Branch protection and required checks can support a review process. Review the repository’s actual settings and permissions before relying on them.

6.14 · Scripting GitHub

Read data with the API

GitHub’s REST API exposes resources such as repositories, issues, and pull requests over HTTP.

TERMINAL · PUBLIC REPOSITORY EXAMPLE
curl https://api.github.com/repos/octocat/Hello-World

The response is JSON. This public example does not need a token; private resources and many other operations require appropriate authentication and permissions. Unauthenticated requests are subject to rate limits.

Sources: Pro Git · Scripting GitHub ↗ · GitHub Docs · REST API Authentication ↗

6.14 · Scripting GitHub

Automate with care

Credentials

Choose an authentication method suited to the task and grant only the necessary permissions. Store tokens in a suitable secret store, outside source code.

Responses

Check HTTP status and rate-limit information. For list endpoints, follow pagination links when there are more results.

Libraries such as Octokit provide API clients. Consult current GitHub API documentation for endpoint permissions and authentication; older examples in the book may differ from current requirements.

6.15 · Summary

Work together on GitHub

  1. Create a repository and work through a branch, pull request, review, and merge.
  2. Set up account security and choose an appropriate method for Git authentication.

  5. Package versions with tags, release notes, assets, and verified release links.

  8. Plan and track work with issues, relationships, and Projects.

  10. Use organizations, teams, and roles to coordinate shared access.
  11. Create a branch or fork, publish a change, and open a pull request against the right base.
  12. Discuss feedback and update the contribution as needed.
  13. Review and integrate changes according to the repository’s rules.
  14. Use GitHub’s API with suitable permissions, secret handling, and response checks.
