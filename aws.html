EC2 · Standard vs Unlimited credit mode

Know what happens after credits run low.

The credit mode changes how CPU bursting behaves after an instance exhausts its accrued credits.

S

Standard

Burst using accrued credits. When the balance is depleted, CPU performance gradually returns to baseline until more credits accrue.

Fit: Workloads can tolerate baseline performance after the burst budget is used.
U

Unlimited

Continue bursting using surplus credits. Below-baseline time pays down surplus; sustained average CPU above baseline can incur an additional charge.

Fit: Workloads need to sustain occasional longer spikes and cost is monitored.
Observe: Monitor CPU utilization, CPUCreditBalance, and CPUCreditUsage in CloudWatch. Credit details and persistence differ across generations and states.

EC2 · Reboot or stop and start

Reboot preserves the host session; stop/start replaces it.

Use reboot for an operating system restart. Use stop/start for EBS-backed instances when you need a stopped state or new host placement.

↻

Reboot

Usually remains on the same host, preserves public/private addresses and instance-store data, and does not start a new one-minute minimum billing period.

Ⅱ

Stop → start

Available for EBS-root instances. Compute billing pauses when stopping; EBS volumes remain. Start may move the instance to new hardware.

ADDRESS

Private IPv4 and IPv6 are retained. Auto-assigned public IPv4 usually changes after stop/start; Elastic IP remains associated.

TEMPORARY DATA

Reboot preserves instance-store data. Stop/start erases instance-store data.

SHUTDOWN SAFETY

Prefer EC2 console, CLI, or API for user-initiated state changes. Skipping graceful OS shutdown can risk data integrity.

Before stopping: Check that the root volume is EBS-backed, protect instance-store data, plan for public IP changes, and account for EBS charges while stopped.

EC2 · Hibernate

Resume the operating system from saved memory.

Hibernate is suspend-to-disk: EC2 saves RAM to the EBS root volume and reloads it at the next start.

1
Enable it before launchThe instance must meet EC2 hibernation prerequisites and have a suitably sized encrypted EBS root volume.
2
Hibernation writes memory to diskThe OS is signaled to hibernate; root and attached EBS data volumes persist.
3
Start and resumeRAM contents reload, processes resume, attached EBS data volumes reattach, and the instance ID remains.
Cost detail: Instance usage is not billed while hibernated in the stopped state, but EBS storage charges include the saved RAM image. Usage is billed during the stopping phase.

EC2 · Instance retirement

Retirement is a hardware event; respond before the deadline.

AWS schedules retirement when host hardware has an irreparable failure. The recovery path depends on the root volume type.

EBS root

The instance is stopped. Stop/start it before the event where possible; start migrates it to new hardware. Back up with an AMI or snapshots.

Instance-store root

The instance is terminated and cannot be reused. Back up or migrate important data before the retirement date; instance-store data is lost.

1
Find scheduled eventsCheck EC2 Dashboard events, notifications, or instance status events in each Region.
2
Check reachability and backupCreate an EBS-backed AMI or snapshots before the event when the instance is available.
3
Plan recoveryFor EBS root, schedule a stop/start; for instance-store root, migrate or replace before retirement.
Do not wait: AWS recommends acting promptly because the instance may already be unreachable, and missed retirement can mean downtime or data loss.

EC2 · Automatic instance recovery

Recover from host faults; keep the instance identity.

Automatic recovery attempts to move a supported instance from a failing host to healthy hardware when its system status check fails.

1
Detect an infrastructure problemSystem status checks monitor AWS host infrastructure. An instance status check failure alone does not trigger this recovery.
2
Recover onto another hostIf successful, the event looks like an unplanned reboot. The instance ID and addresses are retained.
3
Validate and fail over if neededRAM is lost and OS uptime resets. If recovery fails or checks remain unhealthy, investigate or stop/start manually.

EC2 · Metadata security and operations

Use IMDS deliberately. Keep secrets elsewhere.

Treat metadata as an instance-local configuration interface, not a trust boundary. Limit unnecessary access and account for the network path used by containers.

SECURITY

Require IMDSv2

Configure the instance to require IMDSv2 where compatible. A tokenized request adds a session step and helps mitigate some request-forgery risks.

SECRETS

Do not put credentials in user data

Anyone or software with instance access may read metadata and user data. Use IAM roles for AWS API access, and a suitable secrets service for application secrets.

NETWORK

Check container hop limits

With IMDSv2, a hop limit of 1 can prevent a container from receiving the response across an extra network hop. Raise it only when needed and understand the exposure.

Know the service limits

Metadata requests are free. Link-local services share a 1,024 packets-per-second limit per instance; avoid excessive polling and cache values where appropriate.

Handle bootstrap carefully

User data is opaque input, has a 16 KB raw limit before Base64 encoding, and is not automatically rerun just because its value is changed on a stopped instance.

Architect’s rule: Restrict who can access the instance, use least-privilege IAM roles, prefer IMDSv2, and never rely on metadata obscurity to protect sensitive values.

EC2 · Elastic IP lifecycle

Allocate, associate, and move a stable IPv4.

An Elastic IP (EIP) is a static public IPv4 allocated to an AWS account in a specific Region. Associate it with an instance or network interface when a stable public endpoint is required.

IPv4 only

EIPs are public IPv4 addresses; EC2 does not support Elastic IP addresses for IPv6.

Region and border group

An EIP is Region-specific and must match the network border group of the resource. It cannot move across Regions.

Outside the VPC, the public hostname resolves to the public IPv4. Within the VPC, it resolves to the instance private IPv4.

EC2 · Network bandwidth

Bandwidth is a ceiling, not a throughput promise.

Instance bandwidth specifications apply independently to inbound and outbound traffic. Realized throughput also depends on flow shape, destination, packet rate, tracked connections, and other instance-level allowances.

Inbound and outbound

A 10 Gbps instance specification means up to 10 Gbps inbound and simultaneously up to 10 Gbps outbound.

Destination matters

Traffic through an internet or local gateway can have different limits from traffic within the Region.

Many flows vs one flow

Aggregate multi-flow bandwidth and single-flow throughput have separate constraints; assess the traffic pattern your application produces.

Do not size from one headline number: Verify instance-specific network performance and test with representative flows, packet sizes, and destinations.

EC2 · Flow limits and burst bandwidth

Baseline and burst behavior depend on instance size.

Some smaller instance types are labeled “up to” and use network I/O credits to burst above baseline. Credits are directional, earned below baseline, and best effort.

Single-flow limits

A single TCP or UDP flow is typically limited to 5 Gbps outside a cluster placement group. Cluster placement groups can raise this up to 10 Gbps; eligible ENA Express pairs can reach up to 25 Gbps.

Ways to use more capacity

Multiple paths with MPTCP can raise aggregate throughput. For gateway traffic, applicable instance and traffic-specific limits still apply.

Credits: Some “up to” instances can burst for a limited period, typically 5–60 minutes depending on size. Separate inbound/outbound buckets apply; after credits run out, traffic returns to baseline. A stopped instance does not earn credits.

EC2 · Placement group strategies

Choose for proximity, fault isolation, or precise time.

Placement groups influence how EC2 places a related set of instances on underlying hardware. Select the strategy based on the failure and communication pattern you need.

CLUSTER · PACK TOGETHER

Low latency, high throughput

Place instances close within one Availability Zone for tightly coupled communication, HPC, or high-throughput node-to-node traffic.

PARTITION · ISOLATE RACKS

Large distributed systems

Separate logical partitions onto distinct racks to reduce correlated failures for replicated systems such as Kafka or Cassandra.

Small critical fleet

Place each instance on distinct hardware to reduce simultaneous failure risk. Rack spread supports up to seven running instances per AZ.

PRECISION TIME

Accurate clock sources

Place supported instances on hardware with enhanced Amazon Time Sync Service access for workloads needing precise synchronization.

EC2 · Network MTU

Match packet size to the narrowest path.

MTU is the largest IP packet size, in bytes, that can traverse a connection. Larger frames reduce per-packet overhead, but every hop on the path must support the selected size.

1500 MTU

Supported by all EC2 instance types and the largest packet size supported over most of the internet.

9001 MTU

Jumbo frames reduce packet overhead. Supported by current-generation instance types and selected previous generations.

Use selectively

Jumbo frames can help within a VPC and are recommended for cluster placement group throughput. Outside-VPC traffic may fragment or slow.

Safe rule: Use 1500 MTU for internet traffic. For mixed routes, set route-aware MTUs or separate interfaces and routes for different path requirements.

EC2 · Path MTU Discovery

Allow PMTUD feedback or oversized packets can stall.

Path MTU Discovery finds the smallest MTU along a route. When a packet is too large, the receiving host or an intermediate device signals the sender to retry with a smaller packet.

Permit the feedback

Security group tracking can allow PMTUD responses for tracked connections. Check security groups and subnet network ACLs for ICMP rules; a NACL can still block feedback.

Test the full route

Validate the instance, VPC route, gateway, VPN or peering, and destination. PMTUD cannot guarantee jumbo frames will pass every router; an internet gateway forwards packets up to 1500 bytes.

Symptom pattern: Small requests succeed while larger transfers hang or drop. Check path MTU, ICMP feedback, and route-specific AWS limits before raising the instance MTU.

The private key proves possession; EC2 keeps the public key.

An EC2 key pair is a public/private credential pair. The public key is installed on the instance; you retain the private key and use it when a connection method requires key-pair authentication.

EC2 • Network security

Security groups are stateful firewalls

A security group controls inbound and outbound traffic for the network interfaces attached to an EC2 instance. Think of it as an allow-list at the instance boundary.

Stateful behavior

When a permitted connection is established, response traffic is automatically allowed—even if a matching reverse-direction rule is absent.

Rules combine as a union

Each network interface can have multiple security groups. Their rules are aggregated; a matching allow in any attached group permits the traffic.

Default posture

A newly created group starts with no inbound allow rules and a default outbound allow-all rule. Tighten egress when your workload needs a narrower policy.

Sources: Security groups

EC2 • Rule design

Build traffic paths with least privilege

Allow only the protocols and sources a tier needs. Prefer references to another security group for tier-to-tier access; use narrow CIDRs for trusted networks.

Public entry

Expose only required web ports (commonly 443, and 80 only when needed). Add IPv6 CIDRs separately when enabling IPv6 access.

Private tiers

Reference the calling tier’s SG as the rule source instead of opening application or database ports to the internet.

Administration

Restrict SSH/RDP to approved admin paths or use managed access. Avoid unrestricted 0.0.0.0/0 or ::/0 access to these ports.

Sources: Security group rules reference

EC2 • Create and change

Create once, adjust safely

Security groups belong to a VPC. Create a clear policy, associate it with the relevant network interface, then refine rules as the application evolves.

Rules update live

Rule changes are automatically applied to associated network interfaces. Existing tracked connections may continue; see connection tracking before expecting immediate interruption.

Multiple groups are additive

Attach multiple groups when useful for modular policy, but remember that any matching allow rule across them can permit traffic.

Plan names and VPC scope

Choose a meaningful name and description at creation. The group’s name and description cannot be changed later; create a replacement if those identifiers must change.

Sources: Create a security group · Change security groups

EC2 • Stateful connection tracking

Rule edits and active flows

Security groups track permitted connections. Because they are stateful, changing a rule does not necessarily tear down traffic that was already tracked.

Diagnose allowance limits

Track the CloudWatch metrics conntrack_allowance_available and conntrack_allowance_exceeded. Exhausted connection-tracking capacity can cause packets to be dropped.

Review routing symmetry

Asymmetric traffic paths can affect connection tracking. Keep request and response paths predictable, especially in multi-interface or appliance designs.

Use the right control

Security groups are stateful instance controls. Network ACLs are stateless subnet controls and can provide explicit deny rules; account for return traffic in both directions.

Source: Security group connection tracking

EC2 • Lifecycle and review

Remove groups with dependency checks

A security group can be deleted only after its attachments and rule references are removed. Treat deletion as a small dependency migration.

Check every interface

Remove the group from all associated instances and network interfaces, or replace it with the intended policy first.

Check rule references

Another group may use this group as a source or destination. Remove or update those referencing rules before deletion.

Review after cleanup

Confirm replacement rules still permit required application paths while avoiding broad access. AWS rejects deletion while dependencies remain.

Amazon EBS supplies scalable block volumes for EC2. Treat the volume as an independently managed storage resource: attach it when needed and protect its data with snapshots.

Independent lifecycle

EBS volumes persist independently from their attached instances. Attach volumes at launch or after launch, and use them like block devices from the operating system.

Protect and restore

Scale online

EC2 • Root volume and instance store

Know what happens when an instance stops

Every instance has one root volume containing its boot image. Its backing type affects stop, recovery, and data-retention behavior.

EBS root is the usual choice

AWS recommends EBS-backed AMIs: instances launch faster and use persistent storage. An EBS-root instance can stop and start while retaining attached-volume data.

Instance store is temporary

Local disks are useful for caches, buffers, scratch data, or replicated temporary data. They are available only on certain instance types; data can be lost when stopped, hibernated, terminated, or when the instance fails.

Protect critical data

Back up instance-store data to persistent storage regularly and design for failure. Root-device type is determined by the AMI; each instance has exactly one root volume.

EC2 automatically runs system, instance, and attached EBS checks every minute. Application checks are opt-in. Each one points to a different failure domain.

System

Status alarm

Handle missing data carefully

AMAZON RDS • RDS PROXY

Put a connection pool in front of the database

RDS Proxy accepts application connections, reuses a smaller pool of database connections, and helps absorb connection surges before they overwhelm an RDS target.

Reuse connections

The proxy keeps database connections open and reuses them, reducing repeated connection setup and the database memory and CPU overhead of many short-lived sessions.

Buffer connection bursts

When the pool is busy, RDS Proxy can queue or throttle requests. If configured limits are exceeded, it can reject connections to protect the database.

Improve failover behavior

For supported Multi-AZ deployments, the proxy tracks the current writer and redirects connections during failover, reducing disruption from DNS caching and reconnect work.

AMAZON RDS • POOLING AND MULTIPLEXING

Transactions borrow connections; sessions can pin them

RDS Proxy multiplexes at transaction boundaries: one transaction uses one underlying database connection, which can return to the pool when the transaction ends.

Transaction boundary

All statements in one transaction use the same underlying connection. After the transaction ends, RDS Proxy can borrow that connection for another session.

Understand pinning

If proxy behavior or session state makes reuse unsafe, the proxy pins the session to one connection until the session ends. Pinning reduces the pooling benefit.

Plan for failover

During a Multi-AZ failover, most client connections can remain open. In-flight statements or transactions can be canceled; new requests may be queued until the writer is ready.

AMAZON VPC • IP ADDRESSING

Allocate address space with CIDR blocks

CIDR notation defines the address range available to a VPC or subnet. Plan the VPC range first, then carve out non-overlapping subnet ranges for workloads and Availability Zones.

VPC IPv4 is required

A VPC must have an IPv4 CIDR block. AWS allows a VPC IPv4 block from /16 through /28; additional IPv4 and IPv6 CIDRs can be associated later, subject to quotas and restrictions.

AMAZON VPC • SUBNET CAPACITY

AMAZON VPC • ROUTE MATCHING

Each route pairs a destination and target

The route table evaluates the packet’s destination against its routes. The local route keeps in-VPC traffic local; other matching routes direct traffic to gateways, connections, or appliances.

Destination

A destination can be an IPv4 or IPv6 CIDR block, or a managed prefix list containing destination ranges.

Target

Targets include local, internet or NAT gateways, VPC peering, VPN, Transit Gateway, gateway endpoints, and supported network interfaces.

Longest prefix match

When multiple routes match a destination, the most specific matching CIDR wins. A peer route therefore takes precedence over a broad default route.

AMAZON VPC • ROUTING PATTERNS

Choose targets to match the traffic path

Route tables can separate internet access, private egress, hybrid connectivity, and service access. Address families use distinct routes and targets.

Internet and private egress

Use an internet gateway default route for public-subnet internet traffic. Private IPv4 internet traffic can route through a NAT device; IPv6 outbound-only traffic uses an egress-only internet gateway.

Private destinations

Route specific network ranges to a VPN, VPC peering connection, or Transit Gateway. Both sides of a peering connection need matching return routes.

AWS service endpoints

Gateway endpoints for S3 or DynamoDB add a prefix-list route to the selected subnet route tables. The more-specific route can bypass a broad NAT route.

AMAZON VPC • GATEWAY ROUTE TABLES

Supported edge targets

Keep traffic symmetric

Respect association constraints

AMAZON VPC • ROUTE PRIORITY

Resolve overlap with specificity and route type

Specific beats broad

A route for a peer CIDR is more specific than 0.0.0.0/0, so matching peer traffic follows the peering route instead of the default route.

Equal destination rules

For the same destination, static routes such as IGW, NAT, ENI, Transit Gateway, peering, and gateway endpoint routes take precedence over propagated routes.

Set the scope

AMAZON VPC • READ FLOW LOG RECORDS

Read a record from flow to verdict

Each record describes an aggregated IP flow for a network interface. Start with endpoints and ports, then use action and logging status to interpret the result.

Trace the flow

Fields include interface, source and destination addresses, ports, protocol, packet and byte counts, and start/end times. The default record is space-separated and uses version 2 fields.

Interpret the action

ACCEPT means traffic was accepted; REJECT can point to security group or network ACL rules, among other causes. Check route and endpoint context too.

Separate traffic from logging status

OK means logging normally; NODATA means no traffic in the interval; SKIPDATA means records were skipped. A dash means a field may not apply or be available.

Configure for useful and cost-aware evidence

Set format for analysis

Default version 2 includes the standard fields. A custom format lets you choose available fields and their order; select only what supports your queries.

Plan delivery and spend

AWS documents typical delivery around 5 minutes to CloudWatch Logs and 10 minutes to S3, on a best-effort basis. Vended log ingestion and archival charges apply; tag destinations to track costs.

Security in the cloud

AMAZON VPC • NETWORK ACLS

Filter at the subnet with a network ACL

Network ACLs apply allow and deny rules at subnet boundaries. They are stateless, so inbound and outbound traffic must be considered independently.

Subnet-level boundary

Every subnet is associated with one network ACL at a time. A single ACL can be associated with multiple subnets; changing the association replaces the previous one.

Stateless behavior

Network ACLs do not remember allowed connections. Add rules for both request and response directions when the return traffic must pass.

Contrast with security groups

Security groups are stateful and are attached to network interfaces. A permitted inbound connection automatically permits its response.

Source: Control subnet traffic with network access control lists

AMAZON VPC • ACL RULE EVALUATION

Number rules for predictable matches

AWS evaluates rules from the lowest number upward and applies the first match. A broad allow placed before a narrower deny can make the deny unreachable.

Match the packet fields

Rules specify a number, traffic type or protocol, port range, source CIDR for inbound or destination CIDR for outbound, and allow or deny.

Use spacing between rules

Rule numbers run from 1 through 32766. Numbering in increments such as 10 or 100 leaves room to insert rules later.

Remember first match

Place a specific deny before a wider allow that would otherwise match first. Changes apply to every subnet associated with that ACL.

Source: Network ACL rules

AMAZON VPC • DEFAULT AND CUSTOM ACLS

Start from defaults, then tighten by subnet

Every VPC has a default network ACL that allows inbound and outbound traffic. Custom ACLs add explicit subnet-level allow and deny policy.

Default ACL behavior

The default ACL allows all inbound and outbound traffic using numbered rules. IPv6 allow rules are present when the VPC has IPv6 configured; the final asterisk rule denies unmatched traffic.

Custom ACL behavior

A custom ACL starts by denying traffic. Add the required inbound and outbound rules before associating it with a subnet, then validate both request and response paths.

Roll out carefully

Each subnet uses one ACL. Replacing an association or editing a shared ACL changes filtering for the affected subnet or all associated subnets.

ELASTIC LOAD BALANCING • REQUEST FLOW

Listeners turn connections into target actions

Clients resolve the load balancer DNS name, connect to a listener, and are routed to a healthy registered target according to the selected load balancer type and its rules.

Listener

A listener checks for connection requests on a configured protocol and port. The target-side protocol and port are also configured.

Target selection

Application Load Balancers evaluate listener rules and select from a target group. Other load balancer types use their corresponding routing behavior.

Health-aware routing

When health checks find a target unhealthy, the load balancer stops sending it traffic; routing resumes after the target becomes healthy again.

ELASTIC LOAD BALANCING • AVAILABILITY AND SCHEME

Place nodes across zones; choose the right front door

Enable the Availability Zones where targets run. Choose an internet-facing load balancer for public entry or an internal one for callers with VPC access.

Internet-facing

Load balancer nodes have public IP addresses and a publicly resolvable DNS name. Targets receive traffic through private IPs and do not need public IPs.

Internal

Nodes use private IP addresses. Callers need access to the load balancer’s VPC to connect.

Enable target zones

Targets in an Availability Zone that is not enabled do not receive traffic. AWS recommends multiple zones; Application Load Balancers require at least two.

APPLICATION LOAD BALANCER • COMPONENTS

Route HTTP requests with application context

An Application Load Balancer operates at OSI layer 7. Listeners accept connections, rules inspect request content, and target groups define where matching traffic goes.

Listener

Configure the client-facing protocol and port. Every listener must have a default rule and can include additional rules.

Rule

Each rule has a priority, conditions, and actions. When conditions match, the listener performs the configured action.

Target group

A target group defines registered targets, the backend protocol and port, and health checks. Health is evaluated for targets in groups used by listener rules.

Source: What is an Application Load Balancer?

APPLICATION LOAD BALANCER • RULE ROUTING

Match request content to the right service

ALB evaluates listener rules in priority order. Conditions can route different hosts, URL paths, headers, methods, query strings, or source IPs to separate target groups.

Route by the request

Path conditions support service routing by URL; host conditions let one ALB serve multiple domains. Header, method, query, and source-IP conditions add further control.

Choose an action

Listener rules can forward to target groups, redirect requests to another URL, or return a custom fixed response.

Keep a default path

Each listener needs a default rule for requests that do not match higher-priority conditions.

Source: Application Load Balancer overview

APPLICATION LOAD BALANCER • TARGET DESIGN

Scale services independently with target groups

Target groups separate health, routing, and scaling for application components. The same instance or IP can serve multiple groups, including different ports.

Define service boundaries

Use separate target groups for services or ports that need different health checks, metrics, or scaling policies. A target can belong to multiple groups.

Choose the routing algorithm

Application Load Balancer target groups use round robin by default; least outstanding requests is an alternative.

Connect application platforms

Targets can include EC2 instances, IP addresses, and Lambda functions. ECS can register tasks using dynamically assigned ports, and Auto Scaling can register or deregister instances automatically.

NETWORK LOAD BALANCER • OVERVIEW

Balance connections at the transport layer

A Network Load Balancer operates at OSI layer 4. It accepts connections on listeners and forwards them to healthy targets using the target group’s configured protocol and port.

Layer 4 forwarding

NLB routes transport-layer connections and flows; listener configuration specifies the client-side protocol and port.

Protocol coverage

Target groups support TCP, UDP, TCP_UDP, TLS, QUIC, and TCP_QUIC. Choose a compatible listener and target group for the application protocol.

Static network entry

NLB creates a network interface and static IP address in each enabled Availability Zone. Internet-facing NLBs can optionally use one Elastic IP per subnet.

Source: What is a Network Load Balancer?

NETWORK LOAD BALANCER • FLOW ROUTING

Keep each flow on a selected target

The listener forwards to a target group. NLB uses flow hashing to choose a target and keeps an individual connection or flow associated with that target for its lifetime.

TCP connections

NLB hashes protocol, source and destination IP addresses and ports, and TCP sequence number. Each individual TCP connection stays with one target for its lifetime.

UDP flows

NLB hashes protocol plus source and destination IP addresses and ports. Packets with the same flow tuple consistently reach the same target.

Per-group health

Health checks are configured per target group. NLB routes to healthy registered targets in the group selected by the listener’s default action.

Source: Network Load Balancer overview

NETWORK LOAD BALANCER • ZONE DESIGN

Plan target health in every enabled zone

NLB nodes send traffic to targets in their own Availability Zone by default. Cross-zone load balancing changes that distribution to include targets in all enabled zones.

Default zone-local distribution

By default, each NLB node routes to registered targets in its own Availability Zone. Enabling cross-zone load balancing lets each node use targets in every enabled zone.

Protect zonal capacity

Enable multiple Availability Zones and keep at least one healthy target per target group in every enabled zone. If a group has no healthy target in a zone, AWS removes that subnet’s NLB IP from DNS.

Plan stable addressing

Each enabled zone gets a static NLB IP. Internet-facing NLBs can use a dedicated Elastic IP address for each enabled subnet.

Source: Network Load Balancer overview

GATEWAY LOAD BALANCER • APPLIANCE FABRIC

Scale inspection appliances in the traffic path

Gateway Load Balancer deploys and scales virtual appliances such as firewalls, intrusion detection and prevention systems, and deep packet inspection systems.

Layer 3 operation

GWLB listens for IP packets across all ports and forwards traffic to the target group configured in its listener.

Keep flows consistent

Flow stickiness sends packets to the same appliance using 5-tuple by default, or configurable 3-tuple and 2-tuple stickiness.

GWLB exchanges application traffic with its registered virtual appliance instances using GENEVE over UDP port 6081.

Provider side

Consumer side

Create a Gateway Load Balancer endpoint for private connectivity to the provider service. The endpoint and application servers must use different subnets.

Route both directions
