01 · The model

What cloud computing changes

Use computing resources over the network when needed, instead of buying and operating all infrastructure ahead of demand.

↗

Provision on demand

Resources can be available in minutes, so teams can respond to new requirements without waiting for hardware procurement.

◷

Pay for consumption

Move from large upfront infrastructure purchases to variable costs tied to the resources you use.

⌘

Choose your building blocks

Combine infrastructure services with higher-level managed services to fit the application and operating model.

Architect’s lens: Cloud changes the speed and economics of capacity decisions. It does not remove the need to design, secure, and operate workloads.

AWS infrastructure is organized into Regions and Availability Zones. Spreading a workload across zones can improve availability and fault tolerance compared with a single data center.

EC2 · Get started

Launch, connect, clean up.

The first-instance workflow is a sequence of choices: image, capacity, identity, network, storage, then a safe connection and lifecycle decision.

01 · CONFIGURE

Choose the launch inputs

Select a Region, AMI, compatible instance type, key pair, VPC/subnet, security group, and root EBS volume.

02 · CONNECT

Use the right access path

Connect to Linux with SSH or Windows with RDP. The network rules and credentials must allow the chosen method.

03 · CLEAN UP

Stop or terminate deliberately

Stop to keep an EBS-backed instance for later. Terminate when finished; instance-store data is lost and configured EBS volumes may be deleted.

Network safety: Avoid SSH or RDP rules open to 0.0.0.0/0 in production. Restrict inbound access to the required source CIDR range.

EC2 · Burstable performance

CPU credits smooth out occasional spikes.

T instances target low-to-moderate average CPU usage with occasional bursts. They earn credits below baseline and spend them above baseline.

=

−
Above baselineSpend accrued credits to burst.
If sustained CPU demand is the normal pattern, compare a fixed-performance instance family instead of relying on bursts.

EC2 · Standard vs Unlimited credit mode

Know what happens after credits run low.

The credit mode changes how CPU bursting behaves after an instance exhausts its accrued credits.

S

Standard

Burst using accrued credits. When the balance is depleted, CPU performance gradually returns to baseline until more credits accrue.

Fit: Workloads can tolerate baseline performance after the burst budget is used.
U

Unlimited

Continue bursting using surplus credits. Below-baseline time pays down surplus; sustained average CPU above baseline can incur an additional charge.

Fit: Workloads need to sustain occasional longer spikes and cost is monitored.
Observe: Monitor CPU utilization, CPUCreditBalance, and CPUCreditUsage in CloudWatch. Credit details and persistence differ across generations and states.

EC2 · Purchasing options

Choose a commitment that matches flexibility.

Separate the compute capacity you run from the billing model or tenancy requirement you choose.

FLEXIBLE · NO TERM

On-Demand

Pay for running time with no long-term commitment. Useful for irregular or short-term workloads that cannot be interrupted.

COMMIT TO USAGE

Savings Plans

Commit to a consistent hourly spend for one or three years for discounts with flexibility across eligible compute usage.

COMMIT TO CONFIGURATION

Reserved Instances

A billing discount applied to matching On-Demand usage. Commitment attributes include family/type, Region, tenancy, and platform.

FLEXIBLE · INTERRUPTIBLE

Spot

Use spare EC2 capacity at a discount. Capacity can be reclaimed; design for interruption and checkpoint work.

DEDICATED TENANCY

Dedicated Instances

Instances run on hardware dedicated to one AWS account; billed per instance, with limited host placement visibility.

HOST CONTROL

Dedicated Hosts

Reserve a physical server with host/socket/core visibility, placement control, and broader BYOL support; billed per host.

Capacity is separate: If you need capacity assured in a specific Availability Zone, consider a Capacity Reservation. A billing discount does not automatically mean capacity is reserved.

EC2 · Instance lifecycle

Choose the state change that fits the outcome.

Reboot, stop, hibernate, and terminate are different operations. They change host placement, preserved data, addresses, and billing differently.

Billing: EC2 compute is billed while running. Stopped instances have no instance usage charge, but EBS storage and other associated resources can still incur charges.

EC2 · Reboot or stop and start

Reboot preserves the host session; stop/start replaces it.

Use reboot for an operating system restart. Use stop/start for EBS-backed instances when you need a stopped state or new host placement.

↻

Reboot

Usually remains on the same host, preserves public/private addresses and instance-store data, and does not start a new one-minute minimum billing period.

Ⅱ

Stop → start

Available for EBS-root instances. Compute billing pauses when stopping; EBS volumes remain. Start may move the instance to new hardware.

ADDRESS

Private IPv4 and IPv6 are retained. Auto-assigned public IPv4 usually changes after stop/start; Elastic IP remains associated.

TEMPORARY DATA

Reboot preserves instance-store data. Stop/start erases instance-store data.

SHUTDOWN SAFETY

Prefer EC2 console, CLI, or API for user-initiated state changes. Skipping graceful OS shutdown can risk data integrity.

Before stopping: Check that the root volume is EBS-backed, protect instance-store data, plan for public IP changes, and account for EBS charges while stopped.

EC2 · Hibernate

Resume the operating system from saved memory.

Hibernate is suspend-to-disk: EC2 saves RAM to the EBS root volume and reloads it at the next start.

1
Enable it before launchThe instance must meet EC2 hibernation prerequisites and have a suitably sized encrypted EBS root volume.
2
Hibernation writes memory to diskThe OS is signaled to hibernate; root and attached EBS data volumes persist.
3
Start and resumeRAM contents reload, processes resume, attached EBS data volumes reattach, and the instance ID remains.
Cost detail: Instance usage is not billed while hibernated in the stopped state, but EBS storage charges include the saved RAM image. Usage is billed during the stopping phase.

EC2 · Terminate deliberately

Termination is permanent. Protect data first.

Once an instance reaches shutting-down or terminated, compute billing stops, but the instance cannot be started or recovered.

✓

Back up what matters

Create AMIs or EBS snapshots and move instance-store data to persistent storage before termination.

EBS

Check DeleteOnTermination

The root EBS volume is deleted by default. Additional EBS volumes are preserved by default, but verify each volume’s setting.

⛨

Use protection

Termination protection blocks termination through console, CLI, or API until disabled.

Check automation: EC2 Auto Scaling or EC2 Fleet may launch replacements or terminate instances as part of their desired-capacity behavior.

EC2 · Instance retirement

Retirement is a hardware event; respond before the deadline.

AWS schedules retirement when host hardware has an irreparable failure. The recovery path depends on the root volume type.

EBS root

The instance is stopped. Stop/start it before the event where possible; start migrates it to new hardware. Back up with an AMI or snapshots.

Instance-store root

The instance is terminated and cannot be reused. Back up or migrate important data before the retirement date; instance-store data is lost.

1
Find scheduled eventsCheck EC2 Dashboard events, notifications, or instance status events in each Region.
2
Check reachability and backupCreate an EBS-backed AMI or snapshots before the event when the instance is available.
3
Plan recoveryFor EBS root, schedule a stop/start; for instance-store root, migrate or replace before retirement.
Do not wait: AWS recommends acting promptly because the instance may already be unreachable, and missed retirement can mean downtime or data loss.

EC2 · Automatic instance recovery

Recover from host faults; keep the instance identity.

Automatic recovery attempts to move a supported instance from a failing host to healthy hardware when its system status check fails.

1
Detect an infrastructure problemSystem status checks monitor AWS host infrastructure. An instance status check failure alone does not trigger this recovery.
2
Recover onto another hostIf successful, the event looks like an unplanned reboot. The instance ID and addresses are retained.
3
Validate and fail over if neededRAM is lost and OS uptime resets. If recovery fails or checks remain unhealthy, investigate or stop/start manually.
Availability boundary: Automatic instance recovery helps one instance recover. Use load balancing and Auto Scaling across healthy instances for application-level resilience.

EC2 · Verify recovery

Use Health events and system metrics together.

An unexpected reboot may be an automatic recovery. Check the recovery event outcome and the host-level status metric around that time.

♥

AWS Health Dashboard

Look for a recovery success or failure event. Simplified recovery uses AWS_EC2_SIMPLIFIED_AUTO_RECOVERY_…; CloudWatch action-based recovery uses AWS_EC2_INSTANCE_AUTO_RECOVERY_….

CW

CloudWatch system metric

Review StatusCheckFailed_System for the same Region and time window. A value of 1 indicates a system-level host issue; 0 indicates the check passed.

Keep context: Recovery events indicate an attempt and its outcome. A system check metric confirms a host-level issue; it does not explain application or guest OS failures.

EC2 · Configure recovery and understand limits

Default recovery is conditional, not a high-availability design.

Simplified automatic recovery is enabled by default at launch for supported instance types, but AWS must have capacity and the instance must meet recovery conditions.

SIMPLIFIED

Default on supported instances

Fixed AWS-managed behavior; no additional recovery charge. Recovery must be configured before a system status check fails.

EC2 · Metadata security and operations

Use IMDS deliberately. Keep secrets elsewhere.

Treat metadata as an instance-local configuration interface, not a trust boundary. Limit unnecessary access and account for the network path used by containers.

SECURITY

Require IMDSv2

Configure the instance to require IMDSv2 where compatible. A tokenized request adds a session step and helps mitigate some request-forgery risks.

SECRETS

Do not put credentials in user data

Anyone or software with instance access may read metadata and user data. Use IAM roles for AWS API access, and a suitable secrets service for application secrets.

NETWORK

Check container hop limits

With IMDSv2, a hop limit of 1 can prevent a container from receiving the response across an extra network hop. Raise it only when needed and understand the exposure.

Know the service limits

Metadata requests are free. Link-local services share a 1,024 packets-per-second limit per instance; avoid excessive polling and cache values where appropriate.

Handle bootstrap carefully

User data is opaque input, has a 16 KB raw limit before Base64 encoding, and is not automatically rerun just because its value is changed on a stopped instance.

Architect’s rule: Restrict who can access the instance, use least-privilege IAM roles, prefer IMDSv2, and never rely on metadata obscurity to protect sensitive values.

EC2 · Elastic IP lifecycle

EC2 · Network bandwidth

Bandwidth is a ceiling, not a throughput promise.

Instance bandwidth specifications apply independently to inbound and outbound traffic. Realized throughput also depends on flow shape, destination, packet rate, tracked connections, and other instance-level allowances.

Inbound and outbound

A 10 Gbps instance specification means up to 10 Gbps inbound and simultaneously up to 10 Gbps outbound.

Destination matters

Traffic through an internet or local gateway can have different limits from traffic within the Region.

Many flows vs one flow

Aggregate multi-flow bandwidth and single-flow throughput have separate constraints; assess the traffic pattern your application produces.

Do not size from one headline number: Verify instance-specific network performance and test with representative flows, packet sizes, and destinations.

EC2 · Flow limits and burst bandwidth

Baseline and burst behavior depend on instance size.

Some smaller instance types are labeled “up to” and use network I/O credits to burst above baseline. Credits are directional, earned below baseline, and best effort.

Single-flow limits

A single TCP or UDP flow is typically limited to 5 Gbps outside a cluster placement group. Cluster placement groups can raise this up to 10 Gbps; eligible ENA Express pairs can reach up to 25 Gbps.

Ways to use more capacity

Multiple paths with MPTCP can raise aggregate throughput. For gateway traffic, applicable instance and traffic-specific limits still apply.

Credits: Some “up to” instances can burst for a limited period, typically 5–60 minutes depending on size. Separate inbound/outbound buckets apply; after credits run out, traffic returns to baseline. A stopped instance does not earn credits.

EC2 · Placement group strategies

Choose for proximity, fault isolation, or precise time.

Placement groups influence how EC2 places a related set of instances on underlying hardware. Select the strategy based on the failure and communication pattern you need.

CLUSTER · PACK TOGETHER

Low latency, high throughput

Place instances close within one Availability Zone for tightly coupled communication, HPC, or high-throughput node-to-node traffic.

PARTITION · ISOLATE RACKS

Large distributed systems

Separate logical partitions onto distinct racks to reduce correlated failures for replicated systems such as Kafka or Cassandra.

SPREAD · DISTINCT HARDWARE

Small critical fleet

Place each instance on distinct hardware to reduce simultaneous failure risk. Rack spread supports up to seven running instances per AZ.

PRECISION TIME

Accurate clock sources

Place supported instances on hardware with enhanced Amazon Time Sync Service access for workloads needing precise synchronization.

Default placement: Without a placement group, EC2 attempts to spread instances across underlying hardware to minimize correlated failures. Placement groups are optional and have no creation charge.

Close placement trades flexibility for communication speed.

One AZ; capacity errors can occur when adding instances or mixing types. Capacity Reservations in cluster groups can reserve matching On-Demand capacity.

Up to seven partitions per AZ. AWS tries to balance instances but does not guarantee even distribution.

Spread limits

Rack spread: maximum seven running instances per AZ. Insufficient unique hardware can cause launch or start failures.

EC2 · Network MTU

Match packet size to the narrowest path.

MTU is the largest IP packet size, in bytes, that can traverse a connection. Larger frames reduce per-packet overhead, but every hop on the path must support the selected size.

1500 MTU

Supported by all EC2 instance types and the largest packet size supported over most of the internet.

9001 MTU

Jumbo frames reduce packet overhead. Supported by current-generation instance types and selected previous generations.

Use selectively

Jumbo frames can help within a VPC and are recommended for cluster placement group throughput. Outside-VPC traffic may fragment or slow.

Safe rule: Use 1500 MTU for internet traffic. For mixed routes, set route-aware MTUs or separate interfaces and routes for different path requirements.
EC2 network MTU ↗

EC2 · Path MTU Discovery

Allow PMTUD feedback or oversized packets can stall.

Path MTU Discovery finds the smallest MTU along a route. When a packet is too large, the receiving host or an intermediate device signals the sender to retry with a smaller packet.

Permit the feedback

Security group tracking can allow PMTUD responses for tracked connections. Check security groups and subnet network ACLs for ICMP rules; a NACL can still block feedback.

Test the full route

Validate the instance, VPC route, gateway, VPN or peering, and destination. PMTUD cannot guarantee jumbo frames will pass every router; an internet gateway forwards packets up to 1500 bytes.

Symptom pattern: Small requests succeed while larger transfers hang or drop. Check path MTU, ICMP feedback, and route-specific AWS limits before raising the instance MTU.

The VPC is the network boundary you configure.

Amazon VPC gives EC2 instances a logically isolated virtual network. Choose address ranges, place subnets across Availability Zones, and define routing, gateways, and security settings.

A default VPC is created in each Region, with a default subnet per AZ, an attached internet gateway, and a main route to the internet gateway. Default subnets also assign public IPs and DNS hostnames.

Custom VPC

Choose CIDR ranges and build subnets for your architecture. Place tiers across multiple AZs when you need high availability, and configure routes and gateways explicitly.

EC2 · Subnet and internet patterns

Subnets define where instances launch; VPC routing and address configuration determine how they communicate with the internet, other VPC resources, or shared-account services.

Direct internet path

Attach an internet gateway and route internet traffic to it. Instances need appropriate public addressing for direct internet communication.

PRIVATE SUBNET

Controlled outbound access

Do not re-assume the same role by default: Use the credentials already supplied to the instance. Self-assumption requires an explicit trust policy and is generally unnecessary unless session tags or a session policy are needed.

EC2 · PassRole and attach roles

Separate permission to pass a role from role permissions.

A human or automation principal needs permission to attach an instance profile and pass its IAM role to EC2. The application then receives only the role permissions.

Role policy

Defines API actions and resources the workload can access.

iam:PassRole

Lets a principal pass a specific role to EC2; it does not grant the principal the role’s runtime permissions.

EC2 association

Requires instance profile association permissions. Console workflows also require iam:ListInstanceProfiles.

Attachment workflow: Attach during launch or to a running/stopped instance. Only one role can be attached at a time; replacing an existing role requires the instance to be running.

EC2 · Key-pair fundamentals

The private key proves possession; EC2 keeps the public key.

An EC2 key pair is a public/private credential pair. The public key is installed on the instance; you retain the private key and use it when a connection method requires key-pair authentication.

Linux

At first boot, the selected public key is added to ~/.ssh/authorized_keys. SSH requires the corresponding private key.

Windows

The private key is used to decrypt the initial administrator password, which is then used with the selected Windows connection method.

Lost private key: EC2 does not retain a copy and cannot recover it. Depending on the instance and configuration, other recovery paths may exist; Session Manager can be used instead of key-pair access when configured.

EC2 · Create a key pair

Select a key type and save the private file immediately.

Create a key pair in the EC2 console or CLI, or create your own and import only the public key. EC2 never stores a copy of the generated private key.

Supported types

EC2 supports 2048-bit SSH-2 RSA keys for Linux and Windows. ED25519 is supported for Linux, not Windows.

File formats

Choose PEM for OpenSSH or PPK for PuTTY. Use the format compatible with the client that will connect.

Protect the file

Store it in a restricted, backed-up location. On macOS/Linux, set a private key file to owner-read only, for example chmod 400.

One-time download: When EC2 creates a key pair, the browser or CLI returns the private key material once. Save it before closing the workflow.

EC2 · Create or import securely

EC2 needs the public half; you control the private half.

You can let EC2 generate the pair, or create a pair with a trusted tool and import its public key. The private key stays under your custody in either workflow.

EC2-generated pair

EC2 records the public key and returns the private key file at creation. Keep the private file safe; a lost file cannot be downloaded again.

Imported pair

Generate keys with a third-party tool and import the public key. Supported inputs include OpenSSH public key format; EC2 does not accept DSA keys.

Use the right access pattern: Key pairs support SSH or Windows password decryption. They do not grant AWS API permissions to applications; attach an IAM role for that purpose.

EC2 • Network security

Security groups are stateful firewalls

A security group controls inbound and outbound traffic for the network interfaces attached to an EC2 instance. Think of it as an allow-list at the instance boundary.

Stateful behavior

When a permitted connection is established, response traffic is automatically allowed—even if a matching reverse-direction rule is absent.

Rules combine as a union

Each network interface can have multiple security groups. Their rules are aggregated; a matching allow in any attached group permits the traffic.

Default posture

A newly created group starts with no inbound allow rules and a default outbound allow-all rule. Tighten egress when your workload needs a narrower policy.

Sources: Security groups

EC2 • Rule design

Build traffic paths with least privilege

Allow only the protocols and sources a tier needs. Prefer references to another security group for tier-to-tier access; use narrow CIDRs for trusted networks.

Public entry

Expose only required web ports (commonly 443, and 80 only when needed). Add IPv6 CIDRs separately when enabling IPv6 access.

Private tiers

Reference the calling tier’s SG as the rule source instead of opening application or database ports to the internet.

Administration

Restrict SSH/RDP to approved admin paths or use managed access. Avoid unrestricted 0.0.0.0/0 or ::/0 access to these ports.

Sources: Security group rules reference

EC2 • Create and change

Create once, adjust safely

Security groups belong to a VPC. Create a clear policy, associate it with the relevant network interface, then refine rules as the application evolves.

Rules update live

Rule changes are automatically applied to associated network interfaces. Existing tracked connections may continue; see connection tracking before expecting immediate interruption.

Multiple groups are additive

Attach multiple groups when useful for modular policy, but remember that any matching allow rule across them can permit traffic.

Plan names and VPC scope

Choose a meaningful name and description at creation. The group’s name and description cannot be changed later; create a replacement if those identifiers must change.

Sources: Create a security group · Change security groups

EC2 • Stateful connection tracking

Rule edits and active flows

Security groups track permitted connections. Because they are stateful, changing a rule does not necessarily tear down traffic that was already tracked.

Diagnose allowance limits

Track the CloudWatch metrics conntrack_allowance_available and conntrack_allowance_exceeded. Exhausted connection-tracking capacity can cause packets to be dropped.

Review routing symmetry

Asymmetric traffic paths can affect connection tracking. Keep request and response paths predictable, especially in multi-interface or appliance designs.

Use the right control

Security groups are stateful instance controls. Network ACLs are stateless subnet controls and can provide explicit deny rules; account for return traffic in both directions.

Source: Security group connection tracking

EC2 • Lifecycle and review

Remove groups with dependency checks

A security group can be deleted only after its attachments and rule references are removed. Treat deletion as a small dependency migration.

Check every interface

Remove the group from all associated instances and network interfaces, or replace it with the intended policy first.

Check rule references

Another group may use this group as a source or destination. Remove or update those referencing rules before deletion.

Review after cleanup

Confirm replacement rules still permit required application paths while avoiding broad access. AWS rejects deletion while dependencies remain.

Sources: Delete a security group · Rules reference

EC2 • Private API access

Reach the EC2 API through a private endpoint

An interface VPC endpoint uses AWS PrivateLink to connect VPC workloads to the Amazon EC2 API without routing API traffic through an internet gateway, NAT device, VPN, or Direct Connect.

Endpoint service name

For the EC2 API, create an interface endpoint for com.amazonaws.region.ec2, replacing region with the AWS Region you use.

Control access at multiple layers

Use IAM permissions for caller identity and API actions, endpoint security groups for network reachability, and an endpoint policy to constrain requests through this endpoint.

Review the default policy

The default endpoint policy allows full access to the EC2 API through the endpoint. A custom policy can scope principals, actions, and resources; validate its CloudTrail and CloudWatch logging implications for failed requests.

EC2 • Storage choices

Match the storage model to the data access pattern

EC2 storage spans block devices attached to one instance, shared file systems mounted by many instances, and object storage accessed through APIs. Combine options when a workload needs more than one model.

Block

EBS provides persistent volumes that can be detached, reattached, snapshotted, and independently retained. Instance store is tied to host and instance lifecycle.

File

EFS and FSx provide managed file system choices for shared application data, with file system features and protocols selected for workload needs.

Object

Use S3 through APIs for objects, backups, and datasets; it is not mounted as a standard block device in the same way as EBS.

Sources: EC2 storage options · Object, file, and cache storage

EC2 • Persistent block storage

EBS volumes live beyond the instance

Amazon EBS supplies scalable block volumes for EC2. Treat the volume as an independently managed storage resource: attach it when needed and protect its data with snapshots.

Independent lifecycle

EBS volumes persist independently from their attached instances. Attach volumes at launch or after launch, and use them like block devices from the operating system.

Protect and restore

Snapshots are point-in-time backups independent of the source volume. Create volumes from snapshots to restore data or migrate across accounts, Regions, and Availability Zones.

Scale online

Increase a volume’s size or performance without detaching it or restarting the instance. Use AWS Backup or Data Lifecycle Manager to automate snapshot retention where appropriate.

Source: Amazon EBS persistent block storage

EC2 • Root volume and instance store

Know what happens when an instance stops

Every instance has one root volume containing its boot image. Its backing type affects stop, recovery, and data-retention behavior.

EBS root is the usual choice

AWS recommends EBS-backed AMIs: instances launch faster and use persistent storage. An EBS-root instance can stop and start while retaining attached-volume data.

Instance store is temporary

Local disks are useful for caches, buffers, scratch data, or replicated temporary data. They are available only on certain instance types; data can be lost when stopped, hibernated, terminated, or when the instance fails.

Protect critical data

Back up instance-store data to persistent storage regularly and design for failure. Root-device type is determined by the AMI; each instance has exactly one root volume.

Sources: Root volumes · Instance store

EC2 • Shared data

Share files across instances with managed file storage

For applications that expect a shared filesystem, mount a managed file service from multiple compute nodes. Select the service and file system based on OS, protocol, throughput, and workload features.

Amazon EFS

Scalable file storage for Linux instances. Mount a file system as a common data source for applications running on multiple EC2 instances.

Amazon FSx

Fully managed file systems for workloads that need Lustre, NetApp ONTAP, OpenZFS, or Windows File Server capabilities.

Amazon File Cache

Consider a high-performance temporary cache when compute workloads need fast access to file data. Use S3 for durable object data and backups instead of treating it as a mounted block disk.

EC2 • Resource scope

Start resource work in the right Region and Zone

EC2 resources are scoped to the AWS Region or Availability Zone where they live. Choose the target location before creating or searching, and confirm the required services and instance capacity are available there.

Regional scope

Resources such as AMIs are Region-specific. Select the Region in the console or specify it explicitly in CLI commands; a CLI default Region is used when none is supplied.

Zonal placement

An EC2 instance launches into a subnet in an Availability Zone. Spread redundant capacity across Zones when the architecture requires Zone-level resilience.

Check availability and quotas

Services may not be available in every Region, and some Regions must be enabled first. Account quotas can prevent launches or starts when capacity limits would be exceeded.

Sources: Manage EC2 resources · Select a Region

EC2 • Find and inspect

Filter locally; use Global View to scan Regions

The EC2 console lists resources in the selected Region. Filters narrow those lists; AWS Global View provides cross-Region visibility for supported resource types, but it is a read-only view.

Combine filters intentionally

In EC2 list views, multiple values for the same attribute generally match any listed value; filters on different attributes narrow results together. API filtering is server-side, while client filtering works on data already loaded.

Use tags and IDs

Search by resource ID, attributes, or tags. Tag-based naming conventions make it easier to find resources across teams and environments.

Global View has a read-only role

Use it to search supported resources across selected Regions and inspect details. It does not modify resources; use the relevant service console for changes.

Sources: Find EC2 resources · AWS Global View

EC2 • Organize with tags

Tags make resource fleets searchable and governable

A tag is a key and optional value that you define. A consistent tag vocabulary supports resource discovery, ownership, cost allocation, and tag-based IAM controls.

Define shared keys

Agree on keys such as Environment, Application, Owner, and CostCenter. Tags are plain strings with no built-in meaning to EC2; consistency creates their operational value.

Automate at creation

Apply tags when resources are created when supported. IAM policies can enforce allowed keys and values or use tags for attribute-based access control.

Know the limits

EC2 allows up to 50 user tags per resource; keys are unique per resource and case-sensitive. Tag values and keys may be visible in many API responses, so keep sensitive data out.

Source: Tag EC2 resources

EC2 • Health checks

Find the failing layer before choosing a repair

EC2 automatically runs system, instance, and attached EBS checks every minute. Application checks are opt-in. Each one points to a different failure domain.

System

Detects underlying host or AWS infrastructure issues. For EBS-backed instances, stop/start can move the instance to a new host.

Instance and EBS

Guest network, memory, filesystem, or kernel issues can fail instance checks. Attached EBS checks test volume reachability and I/O; metric is Nitro-only.

Application

Opt-in HTTP/HTTPS health checks test a configured path, port, and response matcher. Allow the check traffic through instance security groups.

Sources: Status checks · Application checks · View status

EC2 • CloudWatch

Turn sustained health signals into actionable alarms

CloudWatch metrics show trends; alarms evaluate thresholds across periods and can notify operators or invoke configured EC2 actions.

Status alarm

Use StatusCheckFailed or a specific status metric. Set threshold and evaluation windows, then select notification or recovery actions.

Handle missing data carefully

Metric gaps may create insufficient data even when an instance is healthy. Avoid treating missing data as a confirmed failure before disruptive actions.

Add guest visibility

EC2 metrics arrive every five minutes by default. Detailed monitoring enables one-minute periods; the CloudWatch agent adds guest system metrics and logs.

Sources: Monitor with CloudWatch · Create status check alarms

EC2 • EventBridge

Route instance state changes with events

EC2 emits an EventBridge notification when an instance changes state. Match all transitions or narrow the rule to selected states or instances.

What the event tells you

It includes the instance ID, new state, account, Region, and time. States include pending, running, stopping, stopped, shutting-down, and terminated.

Alert pattern

Create an SNS topic, confirm email subscriptions, then create an EventBridge rule for EC2 Instance State-change Notification and select the desired filters.

Test safely

Validate the event pattern and target permissions with a controlled state transition. Make automated responses idempotent.

Sources: State change events · EventBridge example

EC2 • Audit and response

Correlate health signals with change history

When an instance is impaired, combine metrics and state events with the API activity that came before them. CloudTrail explains who made a request, what was requested, and when.

CloudTrail: who changed it?

EC2 API calls, including console actions, are management events. Event history provides searchable past 90-day activity per Region; use a trail or CloudTrail Lake for ongoing retention.

CloudWatch: how is it behaving?

Use metrics and alarms for operational trends; add the CloudWatch agent for guest OS metrics and logs.

Respond to the actual layer

Inspect check type, timing, and recent changes before acting. Treat insufficient metric data as unknown, not confirmed failure.

Sources: CloudTrail · CloudWatch · Monitoring overview
