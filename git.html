1.1 · About Version Control

Keep the history of a project

A version control system records changes so you can revisit a known point in time.

COMPARE

1.1 · Version control models

Where does the history live?

LOCAL

One computer

A local database tracks revisions on one machine. It is useful for individual history but limited for collaboration.

CENTRALIZED

One main server

Clients check out files from a central repository. When that server is unavailable, versioned collaboration stops.

DISTRIBUTED

Many full repositories

A Git clone includes repository history. Local work and commits can continue offline, then be shared later.

Your repositoryFiles + history
↔
Shared remoteFiles + history
↔
Teammate’s repositoryFiles + history

1.2 · A Short History of Git

Built for the Linux kernel

Git was created in 2005 after the Linux kernel project needed a new distributed version control system.

1991–2002

Patches and archives

Kernel changes circulated as patches and archived files.

2002

BitKeeper

The project began using a proprietary distributed system.

2005

Git begins

The BitKeeper relationship ended, prompting a new tool led by Linus Torvalds and the Linux community.

Design goals: speed, simple design, strong branching support, a fully distributed model, and efficiency for large projects.

1.3 · What is Git?

A stream of snapshots

A commit records a snapshot of the project. Unchanged files can reuse the same stored content, so Git does not need to copy everything again.

Commit Aindex.html v1
style.css v1
→
Commit Bindex.html v2
style.css v1
→
Commit Cindex.html v2
style.css v2

Most work is local

View history, compare revisions, and commit while offline.

Integrity is built in

Git identifies stored content by checksums, making unexpected changes detectable.

2.2 · Recording Changes

From edit to commit

TERMINAL · IN YOUR REPOSITORY
git status
git add README.md
git diff --staged
git commit -m "Describe the project"

Stage the current version

2.2 · Recording Changes

Inspect before committing

TERMINAL · REVIEW AND ORGANIZE
git status --short
git diff
git diff --staged
git rm old-file.txt
git mv old-name.txt new-name.txt

git diff compares unstaged changes with the staging area; git diff --staged compares staged changes with the last commit. git rm removes a tracked file and stages its removal; git mv moves and stages a tracked file.

Use .gitignore for files you do not want to add, such as generated output. Ignore rules do not stop tracking files already in Git. Keep credentials out of commits.

2.4 · Undoing Things

Choose what to undo

Unstage a file

After an initial commit, git restore --staged README.md removes its staged changes while leaving working-tree edits in place.

Discard an edit

git restore README.md replaces the file’s working-tree content with its staged version. Uncommitted edits can be lost.

TERMINAL · REVIEW FIRST
git status
git diff
git diff --staged
git restore --staged README.md

Amending: git commit --amend creates a replacement for the latest commit using the staged snapshot. Avoid rewriting commits others have already based work on.

3.1 · Branches in a Nutshell

A branch points to a commit

A Git branch is a movable reference to a commit. Creating a branch starts another line of work from an existing commit.

Commit AShared starting point
→
Commit Bmain points here
→
Commit Cfeature points here

HEAD usually identifies your current branch. A new commit advances that branch; other branch references do not move just because you commit.

TERMINAL · EXPLORE BRANCHES
git branch
git log --oneline --decorate --graph --all

Source: Pro Git · Branches in a Nutshell ↗

3.1 · Branches in a Nutshell

Create a place to work

TERMINAL · START FROM AN EXISTING BRANCH
git switch main
git switch -c feature/login
git branch

git branch feature/login creates a branch without switching to it. git switch -c feature/login creates and switches in one step; the older equivalent is git checkout -b feature/login.

Switching updates the working tree to the target branch. Git may stop a switch if uncommitted changes would be overwritten; inspect git status first.

Source: Pro Git · Branches in a Nutshell ↗

3.2 · Basic Branching and Merging

Merge work into a branch

Complete and commit work on a feature branch, switch to the destination, and merge the feature into it.

TERMINAL · EXAMPLE AFTER COMMITTING THE FEATURE
git status
git switch main
git merge feature/login
git log --oneline --graph --decorate

Fast-forward

If the destination has not diverged, Git may move its branch pointer forward without a merge commit.

Three-way merge

When both lines have diverged, Git combines their changes using a common ancestor and normally creates a merge commit.

Source: Pro Git · Basic Branching and Merging ↗

3.2 · Basic Branching and Merging

Resolve a merge conflict

When Git cannot combine changes automatically, it pauses the merge so you can choose the final content.

  1. Run git status to identify conflicted files.
  2. Edit each file, remove conflict markers, and keep the intended result.
  3. Stage the resolved files with git add, then complete the merge with git commit.
  4. Review the result and run the project’s checks.

During an unfinished merge, git merge --abort attempts to return to the pre-merge state. Starting with a clean working tree makes recovery more reliable.

Source: Pro Git · Basic Branching and Merging ↗

3.3 · Branch Management

Inspect and clean up branches

TERMINAL · LOCAL BRANCHES
git branch -v
git branch --merged
git branch --no-merged
git branch -d feature/login

--merged and --no-merged compare branches against the current branch by default. Switch to the destination branch first if that is the comparison you want.

git branch -d refuses to delete a branch Git considers unmerged. Check its work and upstream before deleting; -D forces deletion and can make unmerged work harder to recover.

3.5 · Remote Branches

Local and remote references

origin/main is a local remote-tracking reference: your last known view of the remote’s main branch.

TERMINAL · FETCH AND INSPECT
git fetch origin
git branch -a
git branch -vv
git log --oneline --graph --decorate --all

3.5 · Remote Branches

Share a feature branch

TERMINAL · PUBLISH YOUR CURRENT FEATURE BRANCH
git switch feature/login
git push -u origin feature/login
git branch -vv

-u sets the upstream for the local branch after a successful push. On another clone, fetch first, then create a local branch that tracks the remote branch:

TERMINAL · TRACK AN EXISTING REMOTE BRANCH
git fetch origin
git switch --track origin/feature/login

These commands require an existing remote and appropriate access; use a branch name that exists in your project.

Source: Pro Git · Remote Branches ↗

3.6 · Rebasing

Replay work on a new base

Rebase reapplies selected commits on another base, usually creating new commit IDs and a more linear history.

TERMINAL · PRIVATE FEATURE BRANCH EXAMPLE
git fetch origin
git switch feature/login
git rebase origin/main

Rebase

Replays commits onto the chosen base. The feature branch receives replacement commits.

Merge

Combines histories without replaying existing commits, and may create a merge commit.

Coordinate before rebasing published commits that others may have used: rewriting shared history can disrupt their work.

Source: Pro Git · Rebasing ↗

3.6 · Rebasing

When a rebase pauses

  1. Inspect the paused operation and conflicted files with git status.
  2. Edit and resolve the files, then stage each resolution with git add.
  3. Run git rebase --continue; repeat if another commit conflicts.
  4. Run git rebase --abort during the operation to cancel and return to the pre-rebase branch state.

Start with a clean working tree and review the resulting history and project checks before sharing changes.

Source: Pro Git · Rebasing ↗

4.1 · The Protocols

Choose access deliberately

SSH

Common for authenticated access. Users need an SSH account or managed key access and suitable repository permissions.

HTTPS

Works through standard web infrastructure. TLS protects the connection; the web service handles authentication and authorization.

Local paths

Convenient when all users can reach the same filesystem, though filesystem permissions and availability still matter.

Git protocol

Useful for intentionally public read access. It provides no authentication or encryption by itself.

4.3 · Generating Your SSH Public Key

Create an SSH key pair

SSH uses a public key to identify a corresponding private key. The public key can be registered with the server or hosting service.

TERMINAL · CREATE A KEY IF YOU NEED ONE
ssh-keygen -t ed25519 -C "your-label"

First check whether you already have a suitable key. At the prompt, choose a new filename without overwriting an existing key and consider a passphrase. The public key is the file ending in .pub; keep the private key private.

Verify the server’s SSH host-key fingerprint through a trusted channel before accepting it on first connection. This helps confirm which server you reached.

Source: Pro Git · Generating Your SSH Public Key ↗

4.4 · Setting Up the Server

Give the right people access

A basic SSH setup combines a server account, authorized public keys, and permissions on a bare repository.

  1. Install Git and configure SSH on the server using your system’s current guidance.
  2. Create or choose a service account and a location for the bare repository.
  3. Register authorized public keys and give the account appropriate filesystem access.
  4. Test clone and push access from a client, then document how access is revoked.

git-shell can restrict an account to Git-related commands, but repository permissions still control which data the account can access. Use account isolation or a managed hosting service if you need finer access control.

4.5 · Git Daemon

Serve public repositories with Git

Git daemon can serve repositories over the git:// protocol. It is often used for anonymous read access.

Export selection

By default, Git daemon serves a repository marked for export with a git-daemon-export-ok file, unless configured to export all.

Access properties

The protocol provides no built-in authentication or encryption. Anyone with network access can read an exported repository.

Use Git daemon only when unauthenticated access is intended. Prefer an authenticated, encrypted transport for private repositories.

EXAMPLE · FETCH REFSPEC
+refs/heads/*:refs/remotes/origin/*

Here remote branches map to local remote-tracking references under origin. The optional leading + permits updates that would otherwise be rejected as non-fast-forward. A repository without a configured origin may return no value.

Appendix A2.1 · Command-line Git

Run a command with arguments

This Node.js example asks Git for a machine-readable status and reports the size of the returned data.

JAVASCRIPT · PASS A REPOSITORY PATH AS THE FIRST ARGUMENT
const { execFile } = require("node:child_process");
const repoPath = process.argv[2];
if (!repoPath) {
  console.error("Usage: node status.js REPO_PATH");
  process.exit(2);
}

execFile("git", ["-C", repoPath, "status", "--porcelain=v1", "-z"],
  { encoding: "buffer", timeout: 10000, maxBuffer: 8 * 1024 * 1024, windowsHide: true },
  function (error, stdout) {
    if (error) {
      console.error("Git failed:", error.message);
      process.exitCode = 1;
      return;
    }
    console.log("Status output:", stdout.length, "bytes");
  });

Save as status.js and run node status.js REPO_PATH with an actual local repository path. The example collects bytes; it does not parse the status entries.

Appendix A2.1 · Command-line Git

Choose stable output

Human-oriented output can depend on Git version, localization, and configuration. Use documented formats intended for scripts where a command offers them.

TERMINAL · STATUS FORMAT FOR PROGRAMS
git status --porcelain=v1 -z

Version 1 porcelain output is designed to remain stable. With -z, filenames are NUL-terminated; rename and copy entries have an additional pathname and a defined order. Parse the documented format instead of splitting on lines or spaces.

Appendix A2.1 · Command-line Git

Treat failures as results

PROCESS

Start or exit

Handle a missing executable, a nonzero exit status, termination, or a timeout. Report enough context to help the user resolve the issue.

REPOSITORY

State and configuration

A path may not be a repository, or Git may reject an operation because of conflicts, permissions, or invalid configuration.

OUTPUT

Buffers and diagnostics

Bound buffered output and handle limits. Standard error can contain progress as well as error details; do not treat it alone as failure.

For large or long-running output, a streaming process API may be more appropriate than buffering the whole response.

Appendix A2.1 · Command-line Git

Control the process context

  1. Use the runtime’s direct process API with a fixed executable and separate argument values; avoid constructing a shell command from input.
  2. Identify the intended repository with a controlled working directory or git -C, and validate operations and input appropriate to your application.
  3. Account for Git configuration, hooks, helpers, environment variables, and repository trust when deciding what an operation may do.
  4. Plan for credentials and interactive prompts. Set appropriate timeouts or cancellation and handle unavailable authentication.

Separate arguments avoid shell parsing, but they do not automatically make arbitrary Git options, URLs, or repositories safe.

Plan for overlapping operations

Several processes may inspect or modify the same repository, index, or working tree at the same time.

Recheck state

Git’s locks protect particular updates; an application may still need its own coordination across a multi-step workflow.
