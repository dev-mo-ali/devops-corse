The mental model · 01 / 19

A setting outside your code

An environment variable is a named text value available to a running process.

Imagine one application running on your laptop and on a server. Its code can stay the same while its settings change: a port, a region, or the name of a deployment environment. Environment variables are one way to pass those settings when starting the application.

NameExample valueWho gives it meaning?
COURSE_ENVdevelopmentOur examples; an application must explicitly read it.
PATHA list of directoriesThe shell and operating system use it to locate executable programs.
AWS_PROFILEtrainingAWS tools use it to select a configured profile.
TF_VAR_environmentdevelopmentTerraform can use it for a declared root input named environment.

Names are agreements

Creating COURSE_ENV=production does not deploy an application or switch an AWS account. A program must recognize the name and decide what to do with its value. There is no universal environment-variable configuration language shared by every program.

Values are text

The value 8080 reaches an application as text. The application decides whether to parse it as a number. Likewise, the text false is not automatically a boolean false; code must interpret it.

Check your understanding: does PORT=9000 open a network port?

No. A program must read PORT, parse the number, and bind to that port. Setting the variable alone only supplies text.

The mental model · 03 / 19

A child gets a copy

Environment values normally flow from a parent process to a child at launch. Later changes do not flow back.

Terminal or IDEStarts a shell
→
Bash / PowerShellPrepares the environment
→
Your programReceives a copy

If you change a value in one terminal, an already-running program or a different terminal is not automatically updated. A child can modify its own environment, but that does not rewrite its parent's values.

Bash on Linux and Windows · 04 / 19

Bash: set, read, and remove

Use an assignment for a shell variable, then export it when child programs need it.

Bash · run in a fresh learning shell
COURSE_LABEL="first lesson"
printf '%s\n' "$COURSE_LABEL"
# Expected: first lesson

export COURSE_ENV="development"
printenv COURSE_ENV
# Expected: development

export COURSE_ENV="staging"
printenv COURSE_ENV
# Expected: staging

unset COURSE_ENV
printenv COURSE_ENV
# No output; printenv returns a nonzero exit status.

Read the syntax

  • NAME=value has no spaces around =. Spaces would change how Bash parses the command.
  • $NAME reads a value. Do not put $ before the name on the left of an assignment.
  • export marks a variable for inheritance by child programs. It does not write a permanent setting.
  • unset removes the variable from the current shell.

For a newly introduced name, plain assignment is shell-local. If a name was already exported or inherited, assigning a new value retains that exported status. Use fresh COURSE_ names when experimenting.

List selectively

Bash · show only course variables
printenv | grep '^COURSE_'

printenv without a name lists the environment. Prefer a specific name during demonstrations so unrelated credentials are not displayed.

Bash on Linux and Windows · 05 / 19

Bash: quotes and missing values

Quote values when they contain spaces, and quote variable expansion when passing a value as one argument.

Bash · double quotes expand; single quotes stay literal
export COURSE_ENV="development"
export COURSE_MESSAGE="Hello from $COURSE_ENV"
printf '%s\n' "$COURSE_MESSAGE"
# Hello from development

export COURSE_LITERAL='Hello from $COURSE_ENV'
printf '%s\n' "$COURSE_LITERAL"
# Hello from $COURSE_ENV

export COURSE_FOLDER="$HOME/course notes"
printf '%s\n' "$COURSE_FOLDER"

"$COURSE_FOLDER" preserves a path with spaces as one argument. Unquoted expansion can split words and expand filename patterns. Portable custom names use letters, digits, and underscores, start with a letter or underscore, and conventionally use uppercase.

Unset and empty are different

Bash · defaults
unset COURSE_OPTION
printf '%s\n' "${COURSE_OPTION-not-set}"
# not-set

COURSE_OPTION=""
printf '%s\n' "${COURSE_OPTION-not-set}"
# An empty line: the variable exists.
printf '%s\n' "${COURSE_OPTION:-fallback}"
# fallback: :- handles both unset and empty.

To require a nonempty value in a script, use : "${COURSE_ENV:?Set COURSE_ENV before running this script}". Failure stops a noninteractive script rather than continuing with a missing setting.

Bash on Linux and Windows · 06 / 19

Bash: limit a value to one command

A command prefix is useful when you want one child process to receive a different setting.

Bash · compare temporary and exported values
export COURSE_ENV="development"
COURSE_ENV="staging" bash -c 'printf "%s\n" "$COURSE_ENV"'
# staging
printf '%s\n' "$COURSE_ENV"
# development

The assignment before bash -c changes that command's environment. The parent keeps its original value. The inner script uses single quotes so the child expands $COURSE_ENV, rather than the parent expanding it too early.

Scope more than one command

Bash · subshell scope
export COURSE_ENV="development"
(
  export COURSE_ENV="testing"
  printenv COURSE_ENV
  # Run other learning commands here.
)
printenv COURSE_ENV
# development

Running versus sourcing

bash setup.sh runs a script in a child; exported values inside it do not update your current shell. source setup.sh executes it in your current Bash session and can change its variables, directory, and settings. Source only a file you understand and trust.

Bash on Linux and Windows · 07 / 19

Linux: make a value available later

Persistence means arranging for future sessions to set the value again.

For your own interactive, non-login Bash sessions, edit your existing ~/.bashrc and add this non-secret setting once:

Bash · line to add to ~/.bashrc
export COURSE_ENV="development"
Bash · reload your reviewed startup file
source ~/.bashrc
printenv COURSE_ENV
Startup contextWhat Bash normally reads
Interactive non-login shell~/.bashrc
Login shell/etc/profile, then the first readable file among ~/.bash_profile, ~/.bash_login, and ~/.profile
Noninteractive scriptDoes not normally read ~/.bashrc; Bash has a separate BASH_ENV mechanism.

A login profile may already source ~/.bashrc. Inspect the existing setup rather than adding duplicate assignments in every startup file.

Other Linux programs

GUI sessions, system services, scheduled tasks, and containers have their own launch configuration. A web service does not automatically read your personal ~/.bashrc. Configure variables in the mechanism that starts that service and restart it when required.

Some Linux login setups read /etc/environment through PAM. It is not a Bash script: do not assume export or $HOME expansion works there. It affects a broader context and is unnecessary for this lab.

Remove a persistent setting

Delete the line you added to the startup file and run unset COURSE_ENV in the current session. Editing the file alone does not erase the value already in memory.

PowerShell and Windows · 08 / 19

PowerShell: use the Env namespace

A normal PowerShell variable and an environment variable are different things.

PowerShell · process-scoped values
$courseLabel = "first lesson"       # Ordinary PowerShell variable
$env:COURSE_ENV = "development"    # Environment variable
$env:COURSE_ENV
# Expected: development

Get-Item Env:COURSE_ENV
# Shows the variable's name and value.

$env:COURSE_ENV = "staging"
Get-ChildItem Env:COURSE_*

Remove-Item Env:COURSE_ENV
Test-Path Env:COURSE_ENV
# Expected: False

$courseLabel is not automatically passed to external programs. $env:COURSE_ENV updates the environment of this PowerShell process and its subsequently launched children. Assignment does not permanently change the Windows user setting.

Quotes

PowerShell · quoting
$env:COURSE_ENV = 'development'
"Current environment: $env:COURSE_ENV"
# Current environment: development
'Current environment: $env:COURSE_ENV'
# Current environment: $env:COURSE_ENV

On Windows, environment names are case-insensitive. On Linux they are case-sensitive, even when using PowerShell. Use one consistent spelling.

PowerShell 7.5+ can retain an empty environment string. Older versions treat empty assignment differently. Use Remove-Item Env:COURSE_ENV when you mean to remove the name; check Test-Path when existence matters.

PowerShell and Windows · 09 / 19

PowerShell: restore after an operation

Use try/finally when temporarily changing a setting for a command or a group of commands.

PowerShell · temporary override with restoration
$courseHadValue = Test-Path Env:COURSE_ENV
$coursePreviousValue = $env:COURSE_ENV

try {
    $env:COURSE_ENV = 'testing'
    # Run your program here; it inherits testing.
    Get-Item Env:COURSE_ENV
}
finally {
    if ($courseHadValue) {
        $env:COURSE_ENV = $coursePreviousValue
    }
    else {
        Remove-Item Env:COURSE_ENV -ErrorAction SilentlyContinue
    }
}

The finally block restores the original value even if the operation throws an error. The existence check preserves the difference between an absent name and a present value on versions that support empty strings.

A PowerShell script block such as & { $env:COURSE_ENV = 'testing' } is not a separate process. Its environment changes can remain in the current process after the block finishes. Ordinary PowerShell variable scope does not isolate environment changes.

Use a child shell for a contained experiment

PowerShell 7 · requires pwsh on PATH
$env:COURSE_ENV = 'development'
pwsh -NoProfile -Command '$env:COURSE_ENV = "child"; $env:COURSE_ENV'
# child
$env:COURSE_ENV
# development

On Windows PowerShell 5.1, the child executable is typically powershell.exe. A child receives the environment even with -NoProfile; that option skips profile scripts.

PowerShell and Windows · 10 / 19

Windows: Process, User, and Machine

Choose the narrowest scope that matches your goal.

ScopeWho receives it?Persistence
ProcessThis process and children launched afterwardEnds with that process.
UserFuture processes launched with the refreshed user environmentStored for your Windows account.
Machine / SystemFuture processes launched with the refreshed machine environmentShared machine setting; changes usually need elevation.
PowerShell on Windows · save a user setting
[Environment]::SetEnvironmentVariable('COURSE_ENV', 'development', 'User')
[Environment]::GetEnvironmentVariable('COURSE_ENV', 'User')
# development

# Set this terminal separately if you want to use it immediately.
$env:COURSE_ENV = 'development'

The stored User value and this terminal's Process value can differ. After a persistent change, start a fresh terminal from a refreshed launcher; restart the whole terminal app or IDE if it keeps supplying the old environment. For ordinary names, user settings generally override machine settings at session construction; PATH has special merging behavior.

Use the Windows interface

  1. Search Start for Edit environment variables for your account.
  2. In User variables, choose New or edit your existing COURSE_ENV entry.
  3. Enter the name and value in their separate fields, without shell syntax or wrapping quotes.
  4. Confirm the dialogs, open a fresh terminal, and inspect $env:COURSE_ENV.

Remove the stored setting

PowerShell on Windows · cleanup
[Environment]::SetEnvironmentVariable('COURSE_ENV', '', 'User')
Remove-Item Env:COURSE_ENV -ErrorAction SilentlyContinue

An empty value passed to this .NET API for User scope deletes the stored variable. This API's persistent-store behavior differs from assigning an empty process value in newer PowerShell.

Where setx fits

Windows · alternative persistent user assignment
setx COURSE_ENV "development"

setx changes future sessions, not this one. Avoid using it to rewrite PATH: it expands references and has a documented 1,024-character assignment limit. Prefer the Windows PATH editor for persistent PATH changes.

PowerShell and Windows · 11 / 19

PowerShell on Linux and shell profiles

The shell syntax travels with PowerShell. Windows registry persistence does not.

In PowerShell on Linux, use $env:COURSE_ENV = 'development' as usual. PATH and Path are different names there. User and Machine registry targets are Windows-specific; they do not provide Linux persistence.

A profile for future PowerShell sessions

PowerShell · inspect and create your own profile if absent
$PROFILE
if (!(Test-Path -LiteralPath $PROFILE)) {
    New-Item -ItemType File -Path $PROFILE -Force | Out-Null
}

Open the displayed file in your editor, preserve its existing contents, and add:

PowerShell · line inside your profile
$env:COURSE_ENV = 'development'

Start a normal new PowerShell session to load it. This configures PowerShell sessions that read that profile; it does not configure every Linux application. Profiles can differ between Windows PowerShell, PowerShell 7, and editor hosts.

To apply your reviewed profile in the current session, run . $PROFILE. To undo the setting, remove the added line and remove the current Env entry. A session started with -NoProfile will skip the profile. On Windows, script execution policy can also prevent loading it; follow the local policy rather than disabling it for this exercise.

WSL and Git Bash

A Windows persistent variable is not a universal shared setting across Windows, WSL, containers, and remote SSH sessions. Set and inspect the value in the environment where the program actually runs. WSL offers an explicit WSLENV bridge when cross-boundary sharing is needed.

Everyday tools · 12 / 19

PATH: how a command is found

PATH is an ordered list of directories searched when an external command is invoked by name.

If terraform is not recognized, the executable may exist but its directory may not be on PATH. Add the directory containing the executable, not the executable filename.

PlatformSeparatorExample entries
Linux:/usr/local/bin:/usr/bin
Windows;C:\Tools;C:\Windows\System32
Bash on Linux · inspect and temporarily prepend
printf '%s\n' "$PATH" | tr ':' '\n'
command -v terraform

# Only if you installed a tool in this directory:
export PATH="$HOME/.local/bin:$PATH"
command -v terraform
PowerShell on Windows · inspect and temporarily prepend
$env:Path -split ';'
Get-Command terraform -ErrorAction SilentlyContinue

# Only if this is your tool's actual installation directory:
$env:Path = 'C:\Tools\Terraform;' + $env:Path
Get-Command terraform -ErrorAction SilentlyContinue

These examples keep the old PATH. Replacing it with only the new directory can make other commands unavailable. Prepending gives that directory priority among PATH entries, so use trusted directories. Aliases, functions, and built-in commands can also affect command resolution; type -a terraform in Bash or Get-Command terraform -All in PowerShell helps identify collisions.

PowerShell on Linux uses the Linux PATH separator. For portable PowerShell, use [IO.Path]::PathSeparator. For permanent changes, edit the appropriate Bash startup configuration or the Windows User PATH list. Remove only the entry you added when cleaning up.

Everyday tools · 13 / 19

.env files are an application convention

A file named .env does nothing until a tool reads it.

.env · illustrative application configuration
COURSE_ENV=development
COURSE_PORT=8080
COURSE_LABEL="Local training"

A framework, runtime option, or dotenv library can read that file and populate the application's environment. Bash, PowerShell, and Terraform do not automatically load every .env file in the current directory. Supported quoting, interpolation, and precedence depend on the loader.

Do not confuse loading with executing

source .env executes the file as Bash code, and ordinary assignments are not necessarily exported. It is not a general dotenv parser. Avoid sourcing unfamiliar files or inventing an eval importer. Use the loader supported by the application.

What belongs in version control?

Keep real credentials out of committed files. A safe .env.example documents required names using dummy values. Ignore local secret-bearing files according to the project convention:

.gitignore · example patterns
.env
.env.*
!.env.example

Ignoring a file does not erase previous commits. If an actual credential was committed, revoke or rotate it and follow the repository's cleanup procedure.

Does Terraform automatically read TF_VAR_environment from a .env file?

No. The variable must be present in the Terraform process environment, or be supplied through another supported input mechanism such as a .tfvars file.

Everyday tools · 14 / 19

Let a program read the value

The same program can read settings from either shell because both pass an environment to the child process.

With Python installed, save this as show_config.py in a learning folder. It prints only the harmless course values.

Python · show_config.py
import os

environment = os.getenv("COURSE_ENV", "development")
port_text = os.getenv("COURSE_PORT", "8080")

try:
    port = int(port_text)
except ValueError:
    raise SystemExit("COURSE_PORT must be an integer.")

if not 1 <= port <= 65535:
    raise SystemExit("COURSE_PORT must be between 1 and 65535.")

print(f"Environment: {environment}")
print(f"Port: {port}")
Bash on Linux · run the program
export COURSE_ENV="staging"
export COURSE_PORT="9000"
python3 show_config.py
PowerShell on Windows · Python launcher installed
$env:COURSE_ENV = 'staging'
$env:COURSE_PORT = '9000'
py show_config.py
Expected output
Environment: staging
Port: 9000

Use your installed Python executable if its name differs; PowerShell on Linux commonly uses python3. Try COURSE_PORT=hello to see validation fail. No server is started by this program.

A missing COURSE_ENV uses the default. An explicitly empty COURSE_ENV remains empty because the code distinguishes absence from an empty string. Applications must decide their own defaults and validation rules.

Everyday tools · 15 / 19

Terraform: inputs versus CLI settings

TF_VAR_ passes root inputs. Other TF_ names configure Terraform itself.

In a fresh directory, save this provider-free example as main.tf:

HCL · no cloud resources
variable "environment" {
  type    = string
  default = "development"
}

output "selected_environment" {
  value = var.environment
}
Bash · provide an input
export TF_VAR_environment="staging"
terraform init
terraform plan
PowerShell · provide the same input
$env:TF_VAR_environment = 'staging'
terraform init
terraform plan

The plan should show the output as staging. The suffix must match the declared variable name, including case. This is a root-module input; child modules receive values through arguments.

When a different value wins

For ordinary local CLI runs, precedence increases from defaults → TF_VAR_ environment values → terraform.tfvars → terraform.tfvars.json → auto.tfvars files in lexical order → explicit -var/-var-file options in their supplied order. Hosted workflows have additional rules.

NamePurpose
TF_VAR_environmentAssign the declared environment input.
TF_LOGEnable Terraform diagnostic logging, for example DEBUG.
TF_LOG_PATHSelect a log file when logging is enabled.
TF_INPUT=0Disable missing-input prompts; it does not approve an apply.

Logs may contain sensitive details. Remove temporary variables after the experiment:

Bash · cleanup
unset TF_VAR_environment TF_LOG TF_LOG_PATH TF_INPUT
PowerShell · cleanup
Remove-Item Env:TF_VAR_environment, Env:TF_LOG, Env:TF_LOG_PATH, Env:TF_INPUT -ErrorAction SilentlyContinue

Everyday tools · 16 / 19

AWS: choose a profile and region

An AWS_PROFILE value selects an existing configuration. It does not create credentials or grant permissions.

Bash · requires an authenticated training profile
export AWS_PROFILE="training"
export AWS_REGION="us-east-1"
aws sts get-caller-identity
PowerShell · same profile selection
$env:AWS_PROFILE = 'training'
$env:AWS_REGION = 'us-east-1'
aws sts get-caller-identity

The identity command reads your account identity; it does not provision resources. Check the returned account before proceeding with an AWS exercise. Avoid publishing that output unnecessarily.

For AWS CLI v2, an explicit --region overrides environment region settings. AWS_REGION takes precedence over AWS_DEFAULT_REGION. Environment credentials can override profile credentials, so an old access-key variable may explain an unexpected identity.

Credential names you may encounter

AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY supply a key pair. Temporary credentials also require AWS_SESSION_TOKEN. Prefer your organization's short-lived login method; never paste real keys into course notes or screenshots.

Keep the namespaces separate

TF_VAR_region feeds a Terraform input only if that input is declared and used. AWS_REGION is read by AWS tools/providers. One does not automatically assign the other.

Practice: prove inheritance yourself

Use a fresh disposable shell and observe what changes, what is inherited, and what stays local.

Run only the example for your shell. These exercises modify process variables only; they do not create persistent user settings.

Lab B · PowerShell 7

pwsh -NoProfile -Command 'Test-Path variable:courseLocal'

Explain your result

In both labs the child can read an environment variable, but changing it in the child leaves the parent value intact. Repeat with another value before running the child and predict the output first.

Extra challenge: why can a new IDE terminal still have an old value?

The IDE may itself still have the old environment. A fresh terminal started by that IDE can inherit the old copy. Restart the application that launches the terminal, not only the terminal tab.

Handle secrets as secrets

Environment variables are configuration transport, not encrypted storage. They may be exposed through child processes, diagnostic logs, process inspection, or CI output. Avoid dumping the whole environment, typing real secrets into recorded shell history, or keeping them in profile files.

Use a secret manager or a platform's protected secret injection for credentials. Only pass secrets to programs that need them. A browser-side application cannot keep a secret merely by calling it an environment variable; values bundled into frontend code are visible to users.
